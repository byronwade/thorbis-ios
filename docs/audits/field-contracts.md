# Field API contracts for native screens

Sources: `Thorbis-TanStack/services/api/openapi.json` (canonical route/request metadata), `services/api/src/app.ts` (actual response wrappers), and the domain `src/schemas.ts`, `src/queries.ts`, and `src/workflow.ts`. The generated OpenAPI document often says only `2XX Success`; response fields below come from the runtime domain schemas and handlers. Examples in `field-schemas.json` are **synthetic schema examples**, never live records.

## Common transport

JSON list endpoints use `{ "items": [/* records */], "nextCursor"?: "opaque" }`, with `?limit=` and `?cursor=` on paged lists. Jobs, estimates, and invoices accept optional `?customerId=` as a narrowing filter; customers accept `?phone=` and `?includeArchived=true`. Contacts, service locations, job notes, and legacy photos return unpaged `{ "items": [...] }`. List items are full domain records, not card projections. `GET /v1/jobs/{id}` returns the Job record **plus** `allowedTransitions`. All timestamps are ISO 8601 strings. Optional domain fields may be omitted; avoid `decodeIfPresent` assumptions that imply required nulls.

The relevant routes declare feature gates (`jobs`, `core_crm`, `estimates`, `invoicing`) and action capabilities in OpenAPI `x-thorbis-*` metadata. Actual checks are resource scoped: jobs can be `assigned`, `locations`, `teams`, or unrestricted; customer, estimate, and invoice list implementations currently return empty for unexpressible assigned/team relationships (and resource reads fail closed). Do not infer access from a role label or a page. Use server failures and available capability decisions; actions still authorize against the exact record. Detailed endpoint metadata is in the JSON file.

## Jobs and progress

`GET /v1/jobs` → paged `Job`. `GET /v1/jobs/{id}` → `Job & { allowedTransitions: JobStatus[] }`. Required Job fields: `id`, `organizationId`, `customerId`, `title`, `status`, `createdAt`, `updatedAt`. Optional fields: `estimateId`, `estimateRevisionNumber`, `locationId`, `teamId`, `notes`, `assignedToUserId`, **`scheduledFor`**, `dispatchedAt`, `enRouteAt`, `arrivedAt`, `arrivalMethod`, `startedAt`, `pausedAt`, `pauseReason`, `pauseNextAction`, `pauseOwnerUserId`, `pauseCycleAuditId`, `lastResumeAuditId`, `scheduleCycleAuditId`, `completedAt`, `canceledAt`. There is no `scheduledAt` or assignee name in the Job API response. `locationId` is the organization's branch scope, not a service-location address. Load a relevant user/profile source separately if a display name is needed.

`POST /v1/jobs/{id}/progress` requires JSON `{ "to": JobProgressTarget }` and capability `job.edit`. Targets are `scheduled`, `dispatched`, `en_route`, `arrived`, `in_progress`, `paused`. The names `start`, `pause`, `resume` are UI actions, not `to` values. `arrived` requires `"arrival":{"method":"manual"|"geofence"}`. `paused` requires `"pause":{"reason":string,"nextAction":string,"ownerUserId"?:uuid}`; the reason and action trim to 1–2000 characters. `en_route` alone may add `etaMinutes` (integer 1–240 or null). A pause-cycle resume uses `to:"in_progress"` plus `expectedPauseAuditId` from the server-resolved activity action; that field triggers the `job_pause_cycle_resume` feature. Return is updated Job. Legal *next states* are in `allowedTransitions`, including `completed` and `canceled`; those terminal targets have separate `/complete` and `/cancel` endpoints. Status progression is not a fixed line: the server allows skips and reversals as defined in `domains/jobs/src/workflow.ts`.

## Customers, contacts, service locations

`GET /v1/customers` → paged Customer; `GET /v1/customers/{id}` → Customer. Required Customer fields: `id`, `organizationId`, `name`, `archived`, `createdAt`, `updatedAt`. Optional profile fields include `locationId`, `email`, `phone`, `address`, `accountType`, `industry`, `referralSource`, `website`, `preferredContact`, `billingTerms`, `creditLimit` (integer minor units), `taxExempt`, `taxExemptId`, and `archiveCycleAuditId`. `POST /v1/customers` requires `name`; full request schema is embedded in `field-schemas.json`.

`GET /v1/customers/{id}/contacts` → `{items: CustomerContact[]}`. A contact requires `id`, `organizationId`, `customerId`, `name`, `primary`, `createdAt`, `updatedAt`; `role`, `email`, `phone` are optional. `POST` same path takes `{name, role?, email?, phone?, primary?}` and returns the contact with 201. Exactly one contact per customer is primary; the server maintains this. `GET /v1/customers/{id}/locations` → `{items: ServiceLocation[]}`. A location requires `id`, `organizationId`, `customerId`, `label`, `kind: "service"|"billing"`, `address`, `createdAt`, `updatedAt`; `notes`, `coordinates:{latitude,longitude}`, `gateCode`, `alarmCode`, `dogOnSite`, `parking` are optional. `POST` same path requires `{label,kind,address}`; those other fields are optional. Both list results are oldest first. The domain calls these *service locations*; they are distinct from the Job/Customer `locationId` scope field.

Archived customer parity uses `GET /v1/customers?includeArchived=true`, which returns active and archived records. TanStack's list views are Recent (active, newest UUIDv7 first), All customers, and Archived; an independent state filter can further narrow each view. Customer Activity is synthetic history, not the generic audit feed: `GET /v1/customers/{customerId}/history?limit=50&cursor=...` returns `{items:[{occurredAt,kind,subjectId,summary}],nextCursor?}`. Each item has those four required string fields; `nextCursor` is omitted when the result has no next page. The endpoint defaults to 50, clamps `limit` to 1–200, and orders descending by time then cursor ID. The mobile UI should show each summary, a kind glyph, and relative time, with “Load earlier activity” for `nextCursor`; a failed next-page request keeps loaded items and can be retried. The history is assembled from contacts, locations, estimates, jobs, invoices, and payments. Each source is capped at 200 records and the response has no truncation indicator. Customer history does not include generic audit actions, and TanStack exposes no Archive or Restore control in the customer UI, even though archive and restore API routes exist.

## Notes and photos/media

`GET /v1/jobs/{id}/notes` → `{items: JobNote[]}` oldest first. Each note requires `id`, `organizationId`, `jobId`, `authorUserId`, `body`, `createdAt`. `POST /v1/jobs/{id}/notes` takes strict `{body}` (trimmed 1–10000 UTF-16 units), requires `job.note`, and returns the note with 201. Notes are append-only.

The legacy photo endpoints are `GET /v1/jobs/{id}/photos` → `{items: JobPhoto[]}` and `POST` with **raw image bytes** and the correct `Content-Type`, not JSON. Allowed types: JPEG, PNG, WebP, HEIC; max 15 MB. The POST requires `job.note`, returns photo metadata with 201; `GET /v1/jobs/{id}/photos/{photoId}` returns raw bytes. New field media should use `POST /v1/jobs/{id}/media` with `{clientAssetId,kind,mime,sizeBytes,originalFilename,contentHash,capturedAt?,tags?,caption?}` (server inserts jobId from path). A successful response is `{asset, uploadTarget?}` or `{asset, resumable?}`; upload bytes to the returned target then `POST /v1/media/{id}/confirm`. `GET /v1/jobs/{id}/media` returns `{items: MediaAsset[],nextCursor?,systemTags:string[]}` newest first and accepts `tag`, `kind`, `includeArchived`, `limit`, `cursor`. Registration needs `job.edit`; read needs `job.view`. New media is archive-only and clientAssetId makes registration retries idempotent. `GET /v1/media/{id}/download` mints a short-lived target after authorization.

## Estimates and invoices

`GET /v1/estimates` / `GET /v1/estimates/{id}` return paged Estimate / Estimate. Required Estimate fields: `id`, `organizationId`, `customerId`, `createdByUserId`, `status` (`draft|sent|approved|declined`), `title`, `lines`, `createdAt`, `updatedAt`. Optional: `locationId`, `currentRevisionNumber`, `options`, lifecycle timestamps. Each line has `id`, `description`, integer `quantity`, `unitPrice:{amount:int,currency:"USD"}` and optional `source`. Total is derived from lines, not a top-level mutable Estimate field. `POST /v1/estimates` takes `{customerId,title,lines:[{description,quantity,unitPrice,source?}],locationId?,options?}` and returns Estimate with 201. `lines` has 1–500 entries; quantity 1–100000; unit amount is integer cents within ±100000000. Options are at most eight mutually exclusive alternatives and trigger `estimate_option_signing`. A negative line or other concession requires `estimate.discount` in addition to `estimate.create`. List/get require `estimate.view`.

`GET /v1/invoices` / `GET /v1/invoices/{id}` return paged Invoice / Invoice. Required Invoice fields: `id`, `organizationId`, `customerId`, `createdByUserId`, `origin`, `sourceOperationKey`, `status` (`draft|issued|paid|void`), `lines`, `linesRevision`, `amountPaid`, `currency:"USD"`, `createdAt`, `updatedAt`. Optional: `jobId`, `locationId`, `scheduleId`, source estimate IDs, `manualPhysicalServiceEvidence`, and lifecycle timestamps. `origin` is `manual|job_completion|progress|deposit|retainage_release|legacy_unknown`. Line shape parallels Estimate lines. `amountPaid` and all prices are integer cents. There is **no direct `POST /v1/invoices`** in the canonical routes. A manually raised invoice is queued as command `invoices.create` through `POST /v1/commands` with payload `{customerId,jobId?,locationId?,manualPhysicalServiceEvidence?,lines:[{description,quantity,unitPrice,source?}],priceBookOverrideReason?}`. The command envelope includes `commandId`, `deviceId`, `actorId`, `organizationId`, `policyVersion`, `command`, `clientCreatedAt`, `payload`; upload body is `{commands:[...]}` and each outcome is `applied|duplicate|rejected`. Permission is `invoice.create`, with conditional `invoice.discount` for concessions and `price_book` feature for direct Price Book source intent. For an existing completed job, `POST /v1/jobs/{id}/completion-invoice` ensures its draft from canonical job/approved estimate facts and requires `invoice.create`. Invoice list/get require `invoice.view`.

`field-schemas.json` contains the exact OpenAPI request components, per-route permission/feature metadata, domain response field lists, transition matrix, and synthetic example bodies. It deliberately does not fabricate successful API response schemas absent from OpenAPI.
