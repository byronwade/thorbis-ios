# Separate Thorbis products: native discovery (2026-10-26)

This is a source inventory for later mobile work, not a claim that a second native app or a production Network release exists. The running staff app's workspace session contract is in [auth-contract.md](auth-contract.md). The Network web product is a different surface, and the two anonymous customer journeys below have different token authorities.

## Entry and identity boundaries

| Surface | Entry and identity | Authority and native implication |
|---|---|---|
| Field Management / operator's business workspace | `apps/web`, `https://app.thorbis.com`; Better Auth session plus active organization. | `/api/auth/get-session`, `/api/auth/organization/list` and `/set-active` establish identity and workspace; `/v1/query/catalog` supplies capabilities, `/v1/features` release/entitlement decisions. The current native staff session belongs only here. `/v1/me` is **not** a workspace proof: it is Network's personal-account projection. [auth contract](auth-contract.md) |
| Thorbis Network public/member product | `apps/network` at the `thorbis.com` product origin; public `/`, `/browse`, `/find`, `/companies/:slug`, `/people/:username`, `/posts/:id`; private `/community`, `/requests`, `/messages`, `/notifications`, `/settings/profile`. Better Auth at `/api/auth/*` sets a personal account cookie. `GET /v1/me` returns `{me:null}` for a visitor. There is no organization plugin in Network auth. | Use a **separate native Network identity/session/cache**, not the staff organization or feature catalog. Network's same-origin web client sends cookies to `/v1/*`; a native client must reproduce cookie-origin behavior. `Network-Expected-Account` on writes detects changed accounts (409). Source: [Network README](../Thorbis-TanStack/apps/network/README.md), [Network auth](../Thorbis-TanStack/apps/network/src/auth-client.ts), [Network client](../Thorbis-TanStack/packages/api-client/src/network-client.ts). |
| Customer estimate/invoice link | Staff sends an issued estimate's `/d/:token` link from `apps/web`; its public bootstrap mounts `DocumentActionPage`, without staff or Network login. `GET /v1/public/document-actions/{token}` resolves a *hashed, revision-bound* token and returns issued paper. | Token authorizes only the linked estimate and its own job/invoices. Never put it in the staff cookie store, analytics, or a generic customer account. A native deep link can present this scoped flow. `apps/portal` is currently a placeholder, not a separate implemented customer-login portal. Source: [route manifest](../Thorbis-TanStack/services/api/src/routes/manifest.ts), [document action page](../Thorbis-TanStack/apps/web/src/features/document-action-page.tsx), [portal placeholder](../Thorbis-TanStack/apps/portal/src/index.ts). |
| Network homeowner guest request | Public company page or assistant obtains one-time consent and opens a request; homeowner reads/acts using an access token in `x-thorbis-guest-access`, **without a Network account**. | Separate from document-action token and member cookie. `POST /v1/guest/consent` binds exact recipient/trade/market/contact/notes; `POST /v1/guest/requests` opens once; `GET/POST /v1/guest/requests[/agree|/withdraw]` uses the guest header. Consent/open use `Idempotency-Key`; agree sends current `offerVersion` and rejects changed proposals. Source: [Network client](../Thorbis-TanStack/packages/api-client/src/network-client.ts), [guest DTOs](../Thorbis-TanStack/packages/api-client/src/network-types.ts), [route manifest](../Thorbis-TanStack/services/api/src/routes/manifest.ts). |

There is no separate general operator-admin mobile API identified in the live route manifest. “Operator” in Network reporting refers to moderation recipients; staff business operations run under organization permissions and features. Provider operations are a server-side gateway, not a shortcut for a mobile operator console. Do not combine Network account capabilities (`canPost`, company authority) with staff `job.view`-style permissions. The [Network direction](../Thorbis-TanStack/docs/product/network-direction.md) distinguishes member, company, work eligibility, and paid-program authority.

## Concrete mobile-feasible slices

| Slice | Implemented API and principal DTOs | Gate / behavior |
|---|---|---|
| Public Network directory | `GET /v1/public/markets` → `NetworkMarketCatalog {cells,trades}`; `GET /v1/public/businesses` → `NetworkPage<NetworkCompanySummary>`; `GET /v1/public/companies/{slug}` → `NetworkCompanyProfile`; `GET /v1/public/people/{username}` → `NetworkPersonProfile`; public posts/profile followers pages and `GET /v1/community/posts/{id}`. | Published projection only. Search location/service are filters, never authority. Directory/company response includes viewer-relative flags and `acceptsGuestRequest`; do not fabricate supply or a verification badge. Anonymous calls need no staff permissions. |
| Network personal account | `/api/auth/sign-up/email`, `/api/auth/sign-in/email`, Better Auth sign-out; `GET /v1/me` → `{me: NetworkMe|null}`, `POST /v1/me/profile` → `NetworkProfile`, `GET /v1/me/username`, `POST /v1/me/username/claim`. `NetworkMe` includes account, profile, username, `capabilities.canPost`, company authority list, unread counts and profile completion. | Network member session, no active organization. Username claim is server-validated and idempotent. `GET /v1/public/auth-providers` advertises providers, but current web sign-in connects email/password; Google/Facebook/X controls are explicitly unconnected pending OAuth cookie review. Never infer an available native OAuth path from the DTO. |
| Member Community | `GET /v1/community/feed?view=local|following|for-you|trade` → `NetworkFeed` (`items`, `nextCursor`); `POST /v1/community/posts` → `NetworkPost`; post like/repost/bookmark and inverse endpoints; `GET /v1/community/search`; follow/unfollow/block/mute and report. | Require current `NetworkMe` and `capabilities.canPost` for composer. Company posting requires `owner` or `publisher` authority, not merely association. Server still decides each action; member-only visibility and blocks affect returned rows. |
| Member messages/requests | `GET /v1/community/conversations`, `GET /.../{id}`, `POST /v1/community/conversations`, `POST /.../{id}/messages`, accept/decline/read; `GET /v1/requests`, `GET /v1/requests/{id}`, `POST /v1/requests/{id}/accept|decline|suggest-time|withdraw`, `POST /.../offers/agree`. DTOs: `NetworkConversationThread {state,canSend,messages,nextCursor}`, `NetworkRequestDetail {role,events,customerContact}`, `NetworkRequest {nextStep,offerVersion,shareContact,status}`. | Member cookie. A block may make a thread 404 rather than returning a blocked status. Company request handling requires owner/publisher authority; proposed next steps are versioned and customer contact is consent-bound. Implement after separate session/cache invalidation, not by reusing staff jobs. |
| Customer estimate action | `GET /v1/public/document-actions/{token}` → `PublicEstimateAction` (`kind:estimate`, title, status, revisionNumber, contentHash, allowedActions, nonce, amount, optional consent/options/acceptance/html). `POST /approve|decline|request-changes` sends revision and nonce; signed approval additionally uses content hash, typed signer name, consent version/consent, optional option id. | Render exact issued paper before action; use returned `allowedActions`, nonce and revision; handle 401 invalid/revoked/expired and 409 stale revision or changed retry payload. The web also has a plain-approval mode only when the response explicitly permits it. |
| Customer related invoices | `GET /v1/public/document-actions/{token}/related`; `GET /.../invoices/{invoiceId}/payments` → paged `PublicInvoicePayments`; `GET /.../document` and `.../payments/{paymentId}/document` return PDFs; `POST /.../pay-link` → `{url}` hosted checkout for the exact balance. | Same customer link only; PDF downloads are private current views. Pay link requires the `payments` feature and configured provider and may return 409 when no payable balance/in-progress/not configured. Native can open hosted checkout externally and re-query state; `/d/return` carries no token and is informational, not payment proof. |

The DTOs and endpoint calls are in [network-types.ts](../Thorbis-TanStack/packages/api-client/src/network-types.ts), [network-client.ts](../Thorbis-TanStack/packages/api-client/src/network-client.ts), and the [live route manifest](../Thorbis-TanStack/services/api/src/routes/manifest.ts). The latter, rather than `contracts/api/network-operations.json`, is the implemented-route source; that contract explicitly contains proposed rows too. Network operations use account self-authority and account-scoped RLS (`permission: "none"` in the tenant route manifest), not the staff `/v1/query/catalog` capability strings. The web additionally uses response fields such as `NetworkCompanyProfile.viewer.authority` and `NetworkMe.capabilities.canPost` to gate controls.

## Provider and release boundaries

The Network origin's Vercel function serves both `/v1/*` and `/api/auth/*`; its production setup requires server-only Better Auth secret, database URL and `PUBLIC_URL`. The frontend README says it remains noindex until publication/SSR/status/rollback gates, so a local route and typed client are not evidence of a public launch. [Network README](../Thorbis-TanStack/apps/network/README.md)

Assistant guest booking is an API flow, but ChatGPT's current documented assistant entry is read-only and cannot yet open or agree a guest request; provider registration and verified egress require separate work. A native guest UI could call the implemented guest endpoints directly with one-time consent, but must not claim that the ChatGPT/Grok handoff is live. Paid Network booking, referrals, job board, creator fund and eligibility economics in the product-direction document are plans, not a native-ready subscription/payment API. [Network direction](../Thorbis-TanStack/docs/product/network-direction.md)

Customer invoice checkout depends on a configured hosted card processor and server provider-operation pinning; native code should not embed card collection or infer success from the return page. The `apps/portal` and `apps/brain` packages remain scaffolds, and the historic [Network preflight](../Thorbis-TanStack/docs/architecture/network-preflight.md) predates current API routes: use current source for implementation status, but preserve its explicit two-app mobile identity boundary.
