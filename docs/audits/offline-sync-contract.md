# Native offline and sync contract (source audit)

This is a source contract, not evidence that a live PowerSync instance is configured. Primary CodeGraph exploration covered `syncScopeFor`, `SyncTokenClaims`, `PowerSyncWebOpener`, `PowerSyncMutationQueue`, and the offline registry; exact route and schema details below come from the named files. The existing `Thorbis-TanStack/apps/ios` project is an online SwiftUI client (`apps/ios/README.md`, `project.yml`, `Thorbis/Sources/API.swift`); it has **no native PowerSync SDK, native SQLite adapter, local command queue, or sync session lifecycle**. `apps/mobile` is an Expo placeholder (`apps/mobile/src/index.ts`, `mobile.manifest.json`). The TypeScript PowerSync package depends on `@powersync/common` and `@powersync/web`, and its concrete opener is web/IndexedDB-specific (`packages/sync-powersync/package.json`, `src/web-opener.ts`). Do not treat the web adapter as a drop-in Swift implementation.

## Read replication authority and transport

`GET /v1/sync/scope` and `GET /v1/sync/token` require an authenticated active organization and the `offline_sync` feature; neither has a standalone capability gate. `syncScopeFor` intersects server stream requests with current resource grants and omits an entity without a grant. `SYNC_STREAM_REQUESTS` requests organization breadth for `customers,locations,jobs,estimates,price_book_items,invoices,appointments,billing_schedules`, but the minted stream may be `assigned`, `team`, `location`, or `organization` only where supported. Feature-disabled resources are omitted. The client cannot request a wider stream. Sources: `services/api/src/app.ts:622-635,1852-1875,2699-2756`; `services/api/src/routes/manifest.ts:4989-5002,5412-5428`; `packages/sync/src/scope.ts:162-173,303-337`; `contracts/sync/scopes.json`.

Token response (synthetic shape, **not a live token**):

```json
{
  "endpoint": "https://<configured-powersync-service>",
  "token": "<server-signed-HS256-JWT>",
  "expiresAt": "2026-10-26T12:05:00.000Z",
  "authorityExpiresAt": "2026-10-26T12:04:00.000Z",
  "scope": {
    "organizationId": "<uuid>",
    "policyVersion": 7,
    "streams": [{"entity":"jobs","scope":"assigned","window":"past_30_days_through_today_plus_7_days","actorId":"<uuid>","teamIds":[],"locationIds":[]}]
  },
  "binding": {"organizationId":"<uuid>","actorId":"<uuid>","policyVersion":7,"generation":"v1.<43-url-safe-base64-characters>"}
}
```

`authorityExpiresAt` is optional. `scope.deviceId` is optional. Token claims carry `sub`, `aud`, `iat`, `exp`, and a server-derived `parameters` object (`organization_id,user_id,policy_version,location_ids,team_ids,streams,jobs_window_dates,jobs_unscheduled,jobs_location_window_buckets,jobs_location_unscheduled`). PowerSync sync rules reference these as `token_parameters`. Default TTL is **five minutes**, capped earlier by conditional authority expiry. These are credentials for the **PowerSync service endpoint returned in the token response**, not for an HTTP change-feed on the Thorbis API. Generated `infrastructure/powersync/sync-rules.yaml` filters provider buckets by those token parameters. Sources: `services/api/openapi.json` schemas `SyncTokenResponse/SyncScope/SyncStream/SyncSessionBinding`; `packages/sync/src/token.ts:20-105`; `packages/sync/src/scope.ts:44-110`; `infrastructure/powersync/sync-rules.yaml:1-9`.

The local read schema is `packages/local-db/src/schema.ts`: 13 synced SQLite tables—`customers`, `jobs`, `job_estimates`, `estimates`, `estimate_revisions`, `price_book_items`, `price_book_item_revisions`, `invoices`, `billing_schedules`, `appointments`, `locations`, `files`, `policy_versions`. `id` is implicit text; values are text/integer/real; money is integer minor units. `jobs` includes `organization_id`, `assigned_to_user_id`, `location_id`, `team_id`, `scheduled_for`, and server-derived `allowed_transitions`; those fields are scope keys, not just UI conveniences. The adapter adds **local-only** `command_queue` and `dead_letters`; they neither replicate nor become a second CRUD upload. `packages/sync-powersync/src/schema.ts:43-111` compiles the local schema into PowerSync types; `src/local-only-registry.ts` owns the two local-only table names. Sync rules are generated from `contracts/sync/scopes.json` plus the local schema, not maintained manually (`tooling/sync/generate-sync-rules.mjs`). Payment instruments, audit events, outbox, and identity users are never synced (`packages/sync/src/scope.ts:130-153`). Job notes have **no local read table**, and the web projection deliberately has no optimistic note row (`packages/sync-powersync/src/web-session.ts:216-230`).

Bind a device database to the server's complete `binding` (`organizationId`, `actorId`, `policyVersion`, `generation`) and exact scope. Generation is a hash of effective actor, organization, policy version, streams, and bucket ids. A different binding must quiesce/rotate the partition and remove the previous data before a new actor/authority reads it; loss of connectivity alone does not prove a rotation. The web implementation names a partition `thorbis-<generation>.db`, validates refreshed credentials against its open binding, and tracks/erases old IndexedDB generations. Native needs its own file ownership, deletion, and lifecycle implementation behind `PowerSyncLocalStateStorage`; do not copy an organization-keyed cache or reopen it under a changed grant. Sources: `packages/sync/src/scope.ts:60-110`; `packages/sync-powersync/src/web-opener.ts:114-125,273-345,474-580`; `src/session-lifecycle.ts:35-115`; `packages/sync/src/workspace.ts`.

## Offline writes and reconciliation

The canonical upload is `POST /v1/commands`, feature `offline_sync`, with `{ "commands": [CommandEnvelope] }`; 1–50 envelopes, at most 64 KiB serialized each. An envelope is `{commandId:uuid,deviceId:uuid,actorId:uuid,organizationId:uuid,policyVersion:int,command:string,clientCreatedAt:ISO8601,payload:object}`. Mint `commandId` once when the user acts and retain it on every retry. Production snapshots supply a positive `policyVersion`; the schema's zero default is a legacy/test compatibility path. A batch returns `{outcomes:[{commandId,status:"applied"|"duplicate",result}|{commandId,status:"rejected",category,detail}]}`. A deterministic rejection is an HTTP 200 per-command outcome; transient 5xx means retain and retry the exact batch. `duplicate` is success for queue clearance. Sources: `packages/sync/src/envelope.ts:1-125`; `services/api/src/app.ts:1755-1835`; `services/api/src/routes/manifest.ts:4900-4987`.

Only `packages/sync/src/registry.ts` entries may queue: `customers.create/update`, `estimates.create/revise/send`, `jobs.createRelatedEstimate/linkEstimate/complete/assign/progress/addNote/acknowledgeCheck/requestFollowUp`, `invoices.create/ensureCompletionDraft/updateLines`. Each declares idempotency and conflict strategy; `jobs.complete` can require `job.edit` in addition to `job.complete` for unpaid disposition. `payments.record/refund`, invoice payment/reversal/void, `jobs.cancel`, schedule Undo, and customer versioned Restore/import are explicitly online-only. Do not queue a REST mutation just because its HTTP endpoint exists. A queued job progress may patch only status/time/allowed-transitions locally; the latter becomes empty until server replication. Completion invoice creation and estimate send wait for canonical replication. Sources: `packages/sync/src/registry.ts:1-150`; `packages/sync-powersync/src/web-session.ts:204-258`; `services/api/src/routes/manifest.ts:4900-4987`.

The product write boundary is an **atomic local transaction** that inserts the envelope into `command_queue` and applies only a registered optimistic projection. `PowerSyncMutationQueue` drains oldest first and filters the active session id; the connector posts commands first and discards PowerSync CRUD transactions **only after** every exact sent command is accounted for. Applied/duplicate outcomes clear queue rows; rejected outcomes go to `dead_letters` for user reconciliation; missing/ambiguous outcomes remain queued. Workspace or authorization generation mismatch blocks old work rather than uploading it under a new identity. Sources: `packages/sync-powersync/src/{projection,queue,connector,session-lifecycle}.ts`; `packages/sync/src/queue.ts:1-185`; `docs/design/powersync-adapter.md`. `packages/local-db/src/database.ts` defines watched SQLite queries and status `{connected,connecting,hasSynced,downloading,lastSyncedAt?,pendingMutations}` for a native adapter.

**Implementable minimum:** keep the current native API screens online until a native PowerSync SDK/SQLite adapter, exact generated schema, token-bound partition lifecycle, and atomic command projector are integrated and tested. A persisted URLSession response cache or a standalone SQLite copy of `/v1/jobs` would lack scope deletion, server change replication, queue replay, and reconciliation, and would not match this contract. The repository contains provider rules and API support, but `services/api/src/sync-provider.ts` makes PowerSync configuration optional. It requires `POWERSYNC_ENDPOINT`, `POWERSYNC_AUDIENCE`, `POWERSYNC_TOKEN_KEY_ID`, `POWERSYNC_TOKEN_SECRET_BASE64URL`, plus deployment attestations (`POWERSYNC_SYNC_RULES_DEPLOYED=true`, `POWERSYNC_REPLICATION_SCOPE_SMOKE_PASSED=true`) for readiness and a live `/probes/liveness` response. Source alone cannot establish a configured production service. Query `GET /v1/ready` and inspect the `powersync` provider verdict in the target environment, then authenticate and obtain `/v1/sync/token` before enabling native offline UI. `offline_sync` is a beta feature (`packages/features/src/catalog.ts:167`); token without configuration returns a dependency error (`services/api/src/app.ts:2712-2719`).

**Observed deployment blocker (2026-10-26 23:35 UTC):** the parent task ran an unauthenticated `GET https://app.thorbis.com/v1/ready` and reported `powersync: not_configured`, with missing configuration names `sync_token_secret`, `sync_token_key_id`, `sync_endpoint`, `sync_audience`. This is an observed production readiness result, not just a source inference; no credential values were returned. Until that provider is configured and verified, the app must show server sync as unavailable and cannot claim a working offline replica. The observation may change after deployment; recheck the endpoint before enabling the feature.

## Remaining workspace destinations and backing routes

The UI navigation catalog is `apps/web/src/navigation/registry.ts:318-616`; capability-only mobile projection is below that file. Route names below are **web destinations**, not automatically API endpoints. Direct HTTP paths are verified against `services/api/openapi.json`; where no collection route exists, native should not invent one.

|---|---|---|

| Work → Team `/team` | `organization.view` | `GET /v1/organization/role-members` plus access/role routes; not a generic `/v1/team`. |
| Work → Fleet `/fleet` | `job.view` | No vehicle/fleet API path in canonical OpenAPI. |
| Customers → Properties `/properties` | `customer.view` | `GET /v1/customers/{id}/locations` and location detail; no cross-customer `/v1/properties` collection. |

`Schedule /schedule` is already represented through Jobs in native UI, but a distinct appointment collection has no `/v1/appointments` route in canonical OpenAPI even though `appointments` is a PowerSync table. The mobile registry can show a destination based on a capability while its actual backing surface is still web-only or query-platform-derived; gate and data source must both be verified before a native destination is offered.

## Observed production readiness (2026-10-26)

Root queried `GET https://app.thorbis.com/v1/ready` without credentials. Response status was `ready` for core services; `powersync` was `not_configured` with missing `sync_token_secret`, `sync_token_key_id`, `sync_endpoint`, and `sync_audience`. This is direct deployment evidence that operational PowerSync cannot presently be validated. Postgres, invoice line writer, Stripe and Resend reported ready. No secrets were returned. Native offline replication remains an unfulfilled requirement; an online-only client is not equivalent to the sync contract.
