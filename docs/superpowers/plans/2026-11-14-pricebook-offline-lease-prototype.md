# Price book offline lease prototype

This experiment lives exclusively in the test target and uses synthetic scopes and an isolated temporary directory. It is not connected to any production entry point or existing cache.

1. Write executable tests for dirty-before-request, restart, authorized commit, write failures, scope/nonce isolation, expiration, and legacy data; run against a deliberately nonfunctional prototype and observe failures.
2. Implement a minimal lease coordinator and file-store test fixture; rerun the focused tests.
3. Record limits: real app integration requires all network entry points to enforce the barrier, cross-process serialization, durable writes, trusted finite authority expiry, and migration. No offline scheme can detect revocation while disconnected.

Baseline: 6 simulator tests executed and failed at `begin()` returning nil in a deliberately unimplemented test-only stub. This baseline does not reproduce or test a production path.

The prototype green run executed 8 simulator tests with zero failures (result bundle `/private/tmp/thorbis-lease-green-1114.xcresult`). These tests exercise a synthetic test-only file store and coordinator. They do not establish production correctness.

Before any integration, identify and gate every price-book request and editor/browse entry point; establish a finite server-backed authority deadline and behavior for legacy leases; add real integration tests including denial during concurrent requests, process termination, all storage-failure combinations, user/organization/origin changes, and offline re-entry. A real design must serialize across all possible processes and bind its records to the actual authority and protected persistence. The prototype's atomic file write and readback do not prove power-loss durability, Keychain behavior, or file protection. Its digest is not authentication against an attacker who can modify both files. Wall-clock rollback and revocation while disconnected are not solved. An uncertain clean write can be readable after an authorized response although the caller receives failure; no durable success is acknowledged in that case.

Follow-up experiment: extend only the synthetic test coordinator with a uniquely named, test-only Keychain service and protected snapshot files. A failing baseline will require a real Keychain item, independently of the file fixture. The service is scoped to a per-test UUID and cleanup is restricted to that service. Real application Keychain items and caches must never be touched. Cross-process locking must cover the full lifetime of any request that can observe denial; same-process actor serialization is insufficient.

Follow-up evidence: `/private/tmp/thorbis-lease-keychain-red-1114.xcresult` ran the synthetic Keychain test against the intentionally file-only adapter; it failed because no Keychain marker existed and a file remained readable after marker deletion. `/private/tmp/thorbis-lease-keychain-green-1114.xcresult` ran 11 test-target cases with zero failures, including three using a UUID-scoped real Keychain service and protected synthetic files. They cover missing markers, policy isolation, legacy files, failed/uncertain writes and reopening. The failure injection happens at adapter boundaries; it does not reproduce every OS or hardware failure.

The separately invoked macOS-only `scripts/experiments/test-pricebook-lease-process.py` compiles a test helper, uses a UUID-scoped Keychain item and temporary lock file, and starts two real processes. Its intentionally unlocked baseline failed because a contender entered; with the advisory lock it excluded the contender, and after forced owner termination the contender acquired the lock and observed the dirty marker. This verifies only those host primitives in that scenario. It is not the iOS coordinator, does not exercise app extensions or signed-device Keychain sharing, and does not establish lock ordering, timeout, file replacement safety, process-start races, or request cancellation semantics. The test coordinator still has no cross-process lock, so it must not be integrated or exposed.

The real catalog's actor, organization, policy, generation, origin, session invalidation and finite server authority deadlines are not yet wired into the prototype. Nor are all request paths gated. Keychain write/readback and atomic protected-file write do not demonstrate power-failure durability or protection when locked on a device. The marker digest is not a cryptographic authentication guarantee. A live implementation requires independent review and real end-to-end interleaving, migration, revocation and failure testing before release.
