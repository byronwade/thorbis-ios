# Customer photo scaling: evidence and implementation plan

**Status:** Proposal, not implemented or qualified. This does not change the current photo rollup or its access rules.

## Measured and inspected behavior

- `CustomerJobCompilationLoader.load` is invoked when the Records tab opens. It loads all customer jobs, customer contacts/locations, estimates and invoices, then serially requests each job's notes, archived-inclusive media, estimate links and job invoices, all customer-history pages, and each job's legacy photos before it publishes the compilation. `fieldMedia` traverses all keyset pages. The legacy `/v1/jobs/:id/photos` repository path returns an unbounded per-job array.
- A DEBUG-only 600-photo fixture was used to observe the existing view (`/private/tmp/thorbis-customer-photo-preview-red2.xcresult`). During the short observation after the first photo became reachable, the unique modern thumbnail-authorization request counter remained at or below 12. The test then failed because an experimental per-job disclosure was absent. This shows the existing `LazyVGrid` did not immediately start 600 thumbnail requests in this simulator scenario; it says nothing about full metadata cost, physical devices, other layouts, or subsequent scrolling. The proposed disclosure was not implemented.
- `MediaThumbnail` obtains a job-authorized signed download URL and downloads the original into a temporary file before local downsampling. `MediaThumbnailCache` is memory-only and scoped to actor, organization, session, authority revision, policy, job and a presentation epoch. The current `/v1/media/:id/download` signs the original storage key; the storage port has no actual derivative-generation/download API. Legacy thumbnails similarly fetch their authorized original bytes (up to 15 MiB).
- The customer rollup currently prevents archived modern media from reappearing through a matching legacy row, deduplicates by storage key within the same job/organization, and preserves a verified legacy fallback only when MIME/size metadata agree. Missing keys, pending media, inconsistent metadata, and failed archived-inclusive reads deliberately produce partial or withheld results. Paging modern rows before resolving all relevant tombstones would violate these guarantees.

## Contract needed for bounded loading

1. Add an explicitly authorized, customer-scoped **photo groups/rollup** read that checks `customer.view` for the customer and `job.view` for every returned job, applies the actual resource-scoped permission decision *before* returning counts or rows, and never exposes other jobs, tenants, storage keys, uploader details or hidden counts. Verify the existing authorization engine can efficiently produce this filtered job set; do not substitute tenant-wide access or aggregate capability alone.
2. Have the server reconcile modern rows—including archived tombstones—and legacy rows for each job **before** cursor slicing and counts. Preserve current `JobPhotoMerge` rules, uncertainty indicators, fallback metadata verification and independent job boundaries. Explicitly specify failures/partial states; never present a partial count as a complete customer total. Include an opaque source type and exact authorized navigation identity for modern and legacy records.
3. Use stable keyset ordering and a bounded maximum (suggested 50) with opaque, versioned cursors tied to customer, query/filter, ordering, actor/organization and the relevant authority/snapshot. Define insert/archive/delete/regrant behavior and expired or invalid cursors. Avoid duplicating or skipping rows through cross-page deduplication or mutable ordering. Add an authorized summary/count only when the server can calculate it from the same reconciled set and permissions; otherwise report a loaded/partial state.
4. Define job grouping so the first response can show job headings and a true customer total without downloading all photo metadata, with continuation per job and explicit retry/load-more. Preserve every photo action and full access to later matches; search and filters must run across the authorized server result, not just a loaded prefix. Notes, documents, estimates, invoices and activity need independently loadable states rather than waiting for all photo pages; retaining their existing scope and completeness checks is mandatory.
5. Build the mobile state machine with source-bound actor, organization, job/customer, policy/authority, session and API-generation identity; synchronously hide invalidated snapshots; cancel or reject stale page responses, detect empty/repeated cursors and mismatched records, preserve prior verified pages on retryable failures, and make refresh/load-more/revoke/regrant/offline states explicit. Do not repurpose full-list APIs whose callers require complete reconciliation.

## Authorized thumbnails

- Define a derivative representation with bounded pixel size and decoded-byte limits, correct orientation, content validation and a lifecycle bound to the original asset. Generate or backfill derivatives in an appropriately isolated server process; preserve the original bytes for detail/export and support older assets/legacy rows without fabricating a thumbnail or weakening tombstone behavior.
- Add a derivative authorization route that rechecks the same owning-job `job.view` resource on every presentation and signs only a tenant-bound derivative key. Keep URL TTL, cache-control, content type, integrity and request-generation rules explicit. An absent derivative must produce a clear bounded fallback or placeholder, not silently expose unverified storage. Consider coalescing duplicate requests only within the same validated scope; never let a cache hit bypass fresh resource authorization.
- Extend retention/archive/delete handling to derivatives, and ensure no raw storage key or signed URL appears in analytics, logs or cross-account caches. Existing full-original downloads may remain for explicit detail/legacy fallback until this contract is implemented.

## Verification gates

- Repository/domain and API tests for 15+20 job photos, modern/legacy duplicate metadata, archived tombstones on a later page, missing keys, duplicate/cursor loops, partial failures, mutable pages, foreign jobs/customers/tenants, resource-scope revoke/regrant and counts; include long-lived in-flight pages and session/API-generation changes.
- Storage/derivative tests for malicious image metadata, decompression limits, orientation, unavailable derivatives, legacy fallback, cross-tenant access, archive/delete and expiry, plus no unauthorized cache reuse or late preview publication.
- iOS UI tests on narrow and large text for job group navigation, exact counts versus partial status, later pages/search/filter, modern/legacy photo opening, cancellation, offline/error/retry and restored permissions. Keep the existing 35-photo and archived/legacy regressions.
- Measure from a reproducible 600+ record account on a physical iPhone, with network shaping and separate cold/warm runs: time to first meaningful content, requests and transferred bytes before scrolling, peak memory, main-thread/frame timing, and incremental-load latency. Compare against the same baseline, preserve sign-in/permission boundaries, and do not infer improvements from source code alone.
- Independently review the API, app and privacy changes; run appropriate server, iOS and signed distribution-boundary checks before any TestFlight build.
