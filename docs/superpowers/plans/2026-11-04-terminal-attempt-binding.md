# Terminal attempt binding plan

**Goal:** Ensure an iPhone reader and its connection token cannot cross a payment attempt, merchant, account environment, workspace, or API session.

**Authority:** The server owns the invoice, durable attempt, connected merchant and environment. Client-visible provider-account identity is prohibited. A connection token must be issued against an authorized, still-open attempt using its server-pinned merchant, and echo only the attempt identifier and Terminal location. A missing or inconsistent binding fails closed. Existing Tap to Pay distribution gate remains disabled.

**Reader lifecycle:** Across all collection controllers, serialize setup through one owner. Before switching binding, disconnect the existing reader, clear Stripe's cached credentials, set the invoice/attempt-bound token provider, and connect using the intent's server location. Validate token attempt and location before returning the secret. Hold exclusive ownership across retrieve, collect and confirm; never swap the token provider during an active collection. Failed disconnect, credential clear, scope/session retirement or missing backend binding prevents further work. Preserve uncertain-attempt recovery rather than creating a new attempt.

**Verification:** Reproduce old-reader reuse with a fake driver. Cover account A→B, same/different location, test/live distinction via server-pinned attempt, overlapping controllers, token/intent mismatch, disconnect or clear failure, cancellation and tenant/session change. Server tests prove cross-invoice, expired, revoked, rerouted and wrong-attempt denial without emitting account identity. Real reader and distribution entitlement are separate qualifications. Until both server contract and client flow are integrated and verified, this work is held and must not claim Tap to Pay readiness.

The concrete SDK adapter is connected only to a hard-disabled qualification seam. A shared owner installs the bound fetch before SDK initialization, excludes concurrent legacy ownership, and serializes discovery completion; SDK-backed lifecycle verification remains outstanding. The legacy collection entry is explicitly fenced off because its bodyless token cannot bind the reader to an attempt and can reuse a stale reader. This fence also stops it creating a server attempt on unsupported devices. The existing distribution flag remains off. The ownership and callback seam tests do not prove SDK callback quiescence, delayed token cache behavior, discovery cancellation, device support or app integration. The coordinator's uncertain state is in memory only and cannot prevent duplicate work across relaunch; a durable recovery owner is still required.

The controller now has an additional hard-disabled bound-flow qualification seam. It records a Keychain marker before a create request and updates it with the observed attempt, provider intent ID, amount and currency before reader collection. An existing marker blocks another attempt, including after relaunch; it contains no client secret. Store tests use a fake, not actual Keychain. There is no operator recovery or server lookup for a lost create response, no qualified Keychain access-group/multiple-process behavior, and no physical reader or SDK callback-lifetime evidence. The marker is a conservative block, not proof that payment reconciliation is implemented. Do not enable either gate on this evidence.

The held server candidate reserves the `tap:` key and exposes a server-authoritative attempt/intent settlement check; neither is deployed or qualified against production transactions. Fresh invoice and payment history alone are insufficient evidence. Marker creation uses an atomic Keychain insert, but Keychain access-group behavior and cross-process update/compare/delete remain unqualified; the recovery check never clears the marker. Cross-process ownership and real SDK lifecycle verification are required before clearance or enabling collection.

The held directory-lease candidate locks the OS-managed app-group container itself, checks descriptor/path identity, and retains the lease after a collection returns or becomes uncertain until the process retires. Separate macOS processes and process termination are covered by local tests. The design assumes every payment writer cooperates and the OS-managed group directory cannot be replaced while locked; neither assumption is established on iPhone. The current Keychain item uses the app's default private access group, not the shared app-group access group, so a different app or extension cannot be assumed to see the same marker. Do not enable release until all entry points use one qualified Keychain access group and stable container, on-device lock/crash/callback behavior is tested, and the server reconciliation contract is deployed and independently qualified. The receipt-release switch remains hard false.

The held lost-create recovery seam persists a UUID before sending the open request, requires the returned attempt to match, and can look up a bound operation after relaunch. A missing or still-unbound operation stays pending; it never authorizes deletion or a new charge. Older markers that lack an operation UUID cannot be reconstructed this way. The server contract and migration are not deployed, and the collection and receipt-release switches remain off.
