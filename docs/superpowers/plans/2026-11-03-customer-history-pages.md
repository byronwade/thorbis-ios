# Customer job-record activity: demand paging

The Jobs section currently waits for every customer-history page in its combined record loader. Change that section to load one page and request subsequent pages only when the person asks. Keep the activity grouped by verified job or account, preserve row navigation, and never imply that a returned cursor ending means the backend's underlying history is complete: the current server caps each source collection at 200 before composing pages.

1. Reproduce eager paging using the new `CustomerJobCompilationTests.testCustomerJobRecordsDoNotLoadAllHistoryPagesImmediately` against unchanged production code. Preserve test log and run this before editing the implementation.
2. Retain the verified job, estimate-to-job and invoice-to-job mapping needed to group later pages. Load exactly one customer-history page during compilation; expose its cursor without displaying total counts as complete. Handle a malformed empty cursor as incomplete.
3. Add an explicitly initiated load-earlier action without repeating photo, note, estimate or invoice requests. Capture the existing customer records scope, request generation, and API generation before each await; publish only if all remain current. Preserve visible rows and cursor on retryable error; reject repeated/empty cursors without a request loop. Do not silently deduplicate distinct history events: their current response contract has no stable event ID.
4. Test grouped append, no eager second page, retry without lost rows, empty/repeated cursor, cancellation and session/permission/API generation changes, and inaccessible records. Check partial-count copy and tappable activity links at large text. Run the existing customer-compilation tests and an independent review before integration.

This slice does not paginate modern media, legacy photos, notes, customer jobs or the backend's constituent history queries. It does not assert complete history or exact counts and is not a TestFlight qualification by itself.
