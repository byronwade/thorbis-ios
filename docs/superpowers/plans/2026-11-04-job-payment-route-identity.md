# Job payment route identity

A technician can tap the next job action, the Money footer, or return from customer view to collect payment. Capture the requested job-scoped invoice and its loaded payment model as one item-based sheet route; never derive the sheet invoice from a later mutable selection. Refuse the transition if the requested ID, current selection, scoped invoice, loaded model ID or model invoice disagree, or if collection is not currently allowed. Recheck current session, workspace, job and capability after asynchronous preparation. Keep the existing cash/check offline decision in the model. Returning from the sheet continues refreshing invoices and closeout. On failure, leave the technician on Money so the current state can be reviewed.

Regression evidence: missing and switched selection, delayed response racing another selected invoice, foreign job scope, stable sheet ownership, current payment state, customer-handoff route, existing cash/check offline and equal-balance invoice selection. No claim of cross-process denial/cached invoice privacy is made by this navigation fix. Review the actual sheet binding and all collection doors independently before release.

Independent review found that a duplicate load could return before an already-loading model finished, and that an open sheet needed to retire on job/customer or authority changes. The revised candidate tracks in-flight reads by model identity, captures the authority token, verifies it at sheet rendering, and dismisses on token changes. A → B → A, changed job/customer, and offline cash/check cases were added. Simulator verification remains pending; a compile alone does not qualify these paths.

The coordinator coalesces reads started by the job owner and waits for a model read already started by the payment sheet. It does not coalesce all model callers: payment reconciliation retains its separate refresh semantics. A gated sheet-owned-read regression is included and still requires simulator verification.

A cancelled waiter on a shared read is retained until that read finishes; the route checks cancellation before presenting. This is an availability/lifetime limitation if the underlying read stalls, not a claim that cancellation aborts the shared operation. The regression cancels one waiter, completes the underlying read and verifies the cancelled caller does not present.

## Bounded mounted-sheet correction

The mounted sheet now retains its invoice/model pair when only the local authority revision changes, while its material token still includes actor, organization, policy and authority generation, API origin and request generation, saved-copy scope revision, job/customer binding and the three required capabilities. Pending asynchronous entry paths still compare the captured authority revision before presenting. This avoids introducing the held experiment's online-only gate and does not prove fresh per-invoice authorization; the durable denial/cache gap remains open. A debug-only mounted test verifies that an unchanged revalidation actually increments the revision without discarding an entered amount, and another verifies that revoking payment permission closes the sheet. An observed denied invoice refresh is tested to stop a new payment attempt; it does not prove cached data is hidden or purged.
