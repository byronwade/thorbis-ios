# Supervised customer photo handoff — prototype (not qualified)

The isolated prototype adds a selected-photo handoff from the staff job media selection bar. It validates an explicit selection of up to 50 currently loaded stored photos against a fresh job read and fresh exact-record reads, then presents one image at a time in the existing protected customer container. Previous/next and swipe are available. It rechecks each exact record before and after a fresh signed-URL download, removes its protected preview file after use, and clears its in-memory image on background or scope invalidation. The endpoint's signed URL is a bearer credential until it expires; a post-download check does not revoke bytes or eliminate the final server/client race.

Status: **not built or released**. Source parsing and two standalone pure Swift harnesses passed for selection and preparation. The initial missing-symbol compilation was not a behavioral red; XCTest and mounted UI tests have not run. The validator, owner, UI, API changes, protected-handback lifecycle, late download cleanup, negative authorization and background cases require independent review and simulator qualification. Exact deployed endpoint contract and online behavior are unverified. Customer selection is read-only; existing staff capture, tagging, archive, share and offline pending flows are intended to remain unchanged but have not been regression-tested with this diff. It is not a remote share or offline customer gallery. Before release, validate signed URL and temp-file cleanup in cancellation/failure paths, real authorization and org/job scope including away-and-back, and visible/recoverable loading or denial states; capture phone/iPad and accessibility evidence.

A DEBUG-only fixture and mounted UI test have been drafted for selecting two photos, customer-only controls, next/previous and authenticated hand-back. The fixture uses in-process metadata and a local sample image; it cannot prove the production transfer or deployed API. The test has not been built or run.

The unrun DEBUG journey coverage now also exercises swiping and an exact asset becoming archived between download and display. The selected-image label is cleared before changing index, and in-progress preparation is invalidated when the media screen disappears. These paths still require an iOS build and the stated device/lifecycle tests.

Invalidation prevents late results from being displayed and clears the current image, but background invalidation does not yet prove immediate cancellation of an already-started storage request. The resulting file must be checked for deletion after late completion and after failures; the transfer cleanup changes affect the existing staff media path too and need dedicated regression coverage.

The prototype now requests cancellation of the active photo task when invalidated; whether a delayed storage transfer actually stops and cleans up is still untested. No cancellation or cleanup guarantee is claimed from that source change alone.

The entry now allows staff with the existing `job.view` media scope to select stored photos. Tag, archive and share remain hidden behind `job.edit`, with additional guards at the mutation entry points. This separation and the backend authorization contract are untested in the deployed environment.

The protected photo cover has been moved to an app-root presenter, following the estimate handoff ownership pattern, so job view removal does not by itself own the cover lifetime. A DEBUG mounted test for revoked job access and protected hand-back is drafted but unrun; coexistence with other customer presentations and real session replacement still needs simulator testing and independent review.

Preliminary simulator run against `34d0cea`: 24 focused unit tests passed; UI tests for archival during download, failed preparation/retry, and job-view revocation under the protected cover passed. Two UI tests failed: the view-only test matched the existing Before filter instead of the tag action (identifiers added in the subsequent draft), and a two-photo handoff showed one photo after a second tile was tapped at the selection-bar boundary. The latter remains unresolved; the later test checks selection state and scroll clearance before handing off. Log: `/private/tmp/thorbis-customer-photo-first.log`; result bundle: `/private/tmp/thorbis-customer-photo-first.xcresult`. This run predates shared customer-mode arbitration and does not qualify later commits.

A later draft protects the estimate-send await with a captured actor, workspace, authority, API and handoff revision; stale completion is not displayed or used to open a fallback. This does not roll back a send already accepted by the server; the record must be refreshed through the normal server-authoritative flow. The draft and its gated regression are not included in the `1ffa44e` test run.

Independent review found performance limits that are not yet resolved: preparation reads each selected asset serially (up to 50 round trips), thumbnail decoding runs on the main actor, and the 50 MiB file check occurs after URLSession downloads the full response. This is not a measured responsive gallery or an on-the-wire byte cap. It fails closed with a retry message when the source scene is unavailable. It handles legacy single-document presentation only; job-document and photo owners still use app-root covers. The old unit state-machine seam does not exercise a UIKit window. The new mounted sheet, session and Pay tests have not run. Multi-scene isolation, scene teardown, accessibility focus, real system authentication, restoration of the previous key window, and Pay ordering still need direct verification. The experiment is not a release candidate.

The experiment now also places an opaque modal shield over the customer window on the originating scene's deactivation and removes it when that scene activates. This is intended to protect the app-switcher snapshot while retaining the staff window underneath. A new background/foreground UI regression has been added but not run; the actual snapshot and system authentication presentation are not yet verified. A system authentication interruption may itself deactivate the scene, and must be tested.
