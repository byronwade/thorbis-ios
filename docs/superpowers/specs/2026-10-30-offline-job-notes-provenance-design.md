# Offline job-note provenance and activity detail — design (not implemented)

## Outcome and boundaries

A technician can read previously verified notes while offline after a cold start, and select a pending or recorded activity entry without crossing actor, workspace, origin, job or permission boundaries. A changed or expired authority cannot make a prior actor's or prior grant's notes visible again. A submitted note is not silently lost or duplicated. Preserve the existing outbox and cached-work experience when the data has verifiable ownership; do not discard an unsent note or label an unverified save as complete. The existing held activity branch is not release-qualified.

## Observed current behavior

- `SessionSnapshot` is device-only Keychain data containing user, active organization, capabilities, feature decisions, policy version and authority/session deadlines. It currently has neither the API origin nor a durable authority revision. Keychain save/clear return no status. A cold offline restore creates a fresh in-memory `authorityRevision`.
- Foreground authority publication rotates in-memory `authorityRevision` on every successful revalidation, including same-policy-version revalidation; an inaccessible server keeps prior verified session authority only until its deadlines. The catalog response includes a generation string, but current code validates that it is nonempty and does not persist it.
- `JobDetailCache` writes job and note JSON under names derived solely from job ID. These files have data protection, but carry no actor, workspace, origin, permission snapshot or cache provenance. `clearAll()` runs on explicit sign-out; changing workspace does not by itself establish that a legacy file belongs to the next actor/workspace.
- `FieldOutbox` has per-actor/workspace queue files, entries contain actor, organization and job identity, and an opaque binding changes on rebind. Its persistence catches and ignores write failures; `enqueue` can return an entry even if the file write failed. Its notes command has a stable command ID when the command endpoint is used.
- Online `saveNote()` sends `POST /v1/jobs/{id}/notes` with only body, appends the response without checking captured authority/job/organization, and clears the text. A connectivity error enqueues a new command even if the REST request may have reached the server. The REST fallback in the outbox likewise retries a note POST without an observed idempotency key. The server's exact deduplication/receipt contract must be verified in the backend before changing retry behavior; do not assume one.

## Proposed durable binding

1. Define an opaque cache authority epoch bound to the **normalized API origin, actor, workspace and verified authorization snapshot**. Persist it inside the same protected Keychain snapshot as its identity, capabilities/features and deadlines. Preserve the same epoch on cold offline restore only when that exact, unexpired snapshot is adopted for the same origin. Expired, invalid, wrong-origin, wrong-identity or missing epochs never authorize cache display.
2. On successful revalidation, compare verified origin, actor, workspace, policy/catalog generation, capabilities and feature decisions. Preserve an epoch only when the effective verified authority is unchanged; rotate before publishing any changed authority, including a revoke and subsequent regrant even when policyVersion is unchanged. The epoch is a local binding, not a server authorization token. A transient network failure does not invent a new grant.
3. Make snapshot write/clear report success. Serialize revalidations and make changed-authority publication and snapshot replacement fail closed with respect to cold-offline cache visibility. Explicitly test Keychain failure and process interruption at each ordering boundary. If a current authority cannot be durably stored, allow authorized live work but do not promise that its newly written cache can be used on a later cold offline launch. Do not leave a revoked previous snapshot usable after a confirmed change.
4. Store notes in a versioned, atomically written, protected envelope with origin, actor, workspace, job, epoch, saved time and note records. Validate all contained `organizationId` and `jobId`, and use collision-resistant path components rather than lossy character filtering. Reads need both a live session scope and an envelope match; recheck them immediately before publishing after any await. Cache data is never proof of server authorization on its own.
5. Retain old-epoch envelopes without presenting them under a new epoch. Refresh/reconcile through an authorized server read before writing a new envelope; do not silently attach old data to a new grant. Store a bounded, clear stale/needs-online state and a recovery action where data cannot yet be reverified. Existing offline notes remain available when their own valid epoch is restored. Do not claim universal continuity across an authority change without an authorized refresh.
6. Legacy job-ID-only files have no provable actor/origin and cannot safely be migrated on identity alone. Preserve them on disk pending an explicit migration/recovery strategy, but never expose them to a different actor or claim they are authorized. Server-confirmed reads can populate a new envelope; don't delete local drafts or queue entries as part of migration. This is a real compatibility gap for legacy cached notes, requiring product review and a release migration plan before rollout.

## View and mutation ownership

- A job status/notes view binds its published data to the exact actor, origin, organization, job, session generation, authority revision and request epoch that produced it. Scope mismatch hides stale content synchronously, before reload tasks run; stale completion cannot publish an error, data, cursor, or cache write. Keep note counts and details tied to the same snapshot, and preserve native back and full text.
- Pending outbox notes may be shown only with the currently verified outbox actor/workspace binding, matching entry actor/org/job, and an independently verified current job scope. Expose pending/rejected status truthfully; a new epoch alone does not prove a cached job belongs to the user.
- A note submission captures immutable input, job/actor/org/origin, view scope and an operation identity before sending. Guard every response and failure after each await. Verify response job/org and preserve newer edits. An authority change must not publish old text or clear a new actor's draft.
- To retry an uncertain note safely, use a backend-confirmed idempotent command or receipt keyed to a durable stable operation ID. Verify the current command endpoint and REST contract; until an exact receipt or idempotency guarantee is proved, an ambiguous REST result needs a recoverable uncertain state and must not automatically create a second submission. A definitive pre-send offline note can be enqueued only after durable queue persistence succeeds; report failure without clearing the draft. Do not delete queued work when a cache or snapshot cannot be refreshed.

## Required evidence before release

- Cold online save, terminate and cold offline restore with matching epoch; contents and pending note survive and are correctly labelled.
- Same-version revoke/regrant; unrelated capability change; actor, workspace, job, origin and device-snapshot mismatch; expired session/authority; late load, cursor, save response and overlapping reload. Old content must never publish into the new scope.
- Snapshot/cache write failures and process interruption at every persistence boundary; no stale authority reused, no false saved state and no lost local draft. Include legacy cache migration with no inferred owner.
- Exact backend command/idempotency/REST fallback tests: response lost after server commit, duplicate command, queue relaunch, policy superseded, conflict/rejection and uncertain recovery. Verify the authoritative persisted receipt.
- Real iPhone/iPad and simulator journey with long multi-paragraph notes, accessibility sizes, VoiceOver, offline/reconnect and permission changes while a detail is open. Inspect rendered screenshots; then independently review the integrated change and run scoped release-boundary checks.

## Decisions still needed from code/contracts

Confirm whether backend authority generation changes for all relevant policy/feature changes, whether resource-specific job access exists, and whether note REST or command receipts guarantee idempotence and permit safe reconciliation. The chosen local epoch does not replace those server contracts. The current branch's unlinked job/invoice fallback remains held until these questions and the required evidence are resolved.

## Backend source inspection — not a deployment claim

At Thorbis-TanStack commit `3dfd7d20c50102e8b6da059d60bae03d2e9458e3`, the [REST notes route](https://github.com/byronwade/Thorbis-TanStack/blob/3dfd7d20c50102e8b6da059d60bae03d2e9458e3/services/api/src/app.ts#L4993) calls the [domain add-note handler](https://github.com/byronwade/Thorbis-TanStack/blob/3dfd7d20c50102e8b6da059d60bae03d2e9458e3/domains/jobs/src/commands.ts#L1122), which authorizes the job and creates a new note ID. The inspected route and handler show no client idempotency key. The [command dispatcher](https://github.com/byronwade/Thorbis-TanStack/blob/3dfd7d20c50102e8b6da059d60bae03d2e9458e3/services/api/src/commands.ts#L245) locks the ledger by organization and command ID and returns a stored result for duplicate commands, but `jobs.addNote` is not in the current-resource replay-reauthorization list or among the intent-fingerprint branches in the inspected source. A policy-version mismatch therefore rejects this replay before returning the old receipt. The current iOS `policy_superseded` REST fallback must not be treated as a safe way to retry an uncertain prior command: it can create another note if the earlier command committed. These findings concern repository source only; verify the deployed version and add backend tests before selecting a delivery strategy.

The inspected backend [job query](https://github.com/byronwade/Thorbis-TanStack/blob/3dfd7d20c50102e8b6da059d60bae03d2e9458e3/domains/jobs/src/queries.ts#L46) authorizes `job.view` on the specific job resource, and [listJobNotes](https://github.com/byronwade/Thorbis-TanStack/blob/3dfd7d20c50102e8b6da059d60bae03d2e9458e3/domains/jobs/src/queries.ts#L134) requires that check. A global `job.view` capability and local epoch are necessary but not sufficient to reauthorize a cached job, especially after assignment changes. A durable resource-scoped grant or existing verified sync/offline policy with explicit validity and revocation semantics must be established before offline reuse is qualified. An earlier successful read proves access only at that time; it does not itself establish an indefinite offline lease. The source inspection does not establish the deployed policy or prove such a contract exists.
