# Invoice editor: uncertain direct writes

The current iOS invoice editor sends `POST /v2/invoices/{id}/lines` with an expected line revision, the replacement lines and an optional price-book override reason. It does not send an idempotency or command ID. The API client invalidates a response when its request generation changes, but that happens after the request may have reached the server. Cancellation or a lost response does not establish that the write failed.

An authorized fresh read of `/v1/invoices/{id}` is necessary for review, but it is not a receipt for this attempt. An unchanged revision at one instant does not prove a delayed request cannot still commit. A changed revision or matching line content does not identify which actor or request wrote it. Do not clear an uncertain-write marker or automatically retry based only on that read.

The server also supports `/v1/commands` with `invoices.updateLines`, an organization-scoped command ID, actor binding and a canonical parsed-intent fingerprint. Command application and its ledger record are transactional. An exact replay is reauthorized and can return the current invoice; if no receipt exists, however, the command may execute the write. It cannot retroactively identify a request sent through the direct endpoint. No read-only command-status endpoint was identified in this audit.

Before wiring recovery or a new keyed submission, verify current actor, organization, API origin, invoice, customer, job, edit authority and live baseline; preserve raw edits and provenance. Define durable write-ahead state, serialization across all actors editing the same invoice, exact request-byte binding, reconciliation and retention. Treat ambiguous or cancelled writes as unresolved until a verified server contract settles them. No production recovery implementation or live backend verification is established by this note.
