# Invoice transport preflight experiment

This worktree is based on merged response-provenance work and carries the held read fence from 3fffee4. No app transport, screen, cache, payment intent, or outbox is connected to this fence.

The standalone macOS harness injects failure while syncing the preflight hold for an existing verified invoice. It checks that begin throws before the caller can start transport, a separate process sees the hold, and unrelated authorized data stays readable. A child process also exits immediately after the failed preflight; a new observer sees the hold. The harness passes. The failed hold itself is not proven durable when its directory sync fails: power loss could remove it, but the guarded contract prevents a live request from having been started in that case.

Existing API provenance reports URLSession/cache policy and saved-copy scope, not fresh authorization or collision-free identity. The fence needs immutable response bytes and verified scope, terminal denial handling even during cancellation, serialized asynchronous cache writers, invalidation of mounted and list consumers, and a tested offline migration before it can be enabled. The held file is not an implementation of those requirements. iOS filesystem protection, device crashes, power loss, extensions, and independently changing assignment authority remain unqualified.

## Held live transport seam and failure matrix

An unwired `fieldFencedInvoice` now performs a fenced live read using the merged provenance. It validates response and request origin, request scope/revision and invoice/tenant IDs, and binds the receipt to exact response bytes. Its task-local request bypasses both the ordinary disk writer and recent-read reuse/publication. This scope comparison is still not proof of a verified job relationship or collision-free identity authority, and the fence does not yet mediate legacy/list caches, payment history, mounted screens or outbox.

The macOS harness covers injected hold-file sync, ledger write and rename, hold removal and final hold-removal sync failures, before transport and during denial. It also proves a canceled/uncertain outcome retains its transport lock for the rest of the process, leaving the pending marker held. This is deliberately conservative and blocks normal retry until app restart; a production design must observe terminal callbacks and release only after quiescence without losing denials. The harness is not proof of iOS device storage, power loss or arbitrary callback races.

Six focused iPhone 17 Pro simulator tests passed (0 failed/skipped) using `/tmp/thorbis-invoice-transport-build/Logs/Test/Test-Thorbis-2026.11.04_14-58-14--0500.xcresult`: live byte binding, preflight refusal, denial after prior read, scope away-and-back, final-origin mismatch, and cancellation preventing another request. They ran against the preceding iOS build, before the final partial-write and record-file-sync harness fault hooks were added. The macOS harness passed with those added hooks. This is not a complete end-to-end privacy or offline qualification.
