# Held customer invoice replacement recovery

The customer invoice book may receive a different invoice from its payment model after its job collection was read. This candidate only gives the description drawer the collection's fresh flag when the displayed invoice exactly equals that original. A different replacement remains fully readable inline, gains an explanation and refresh action, and does not offer sign/pay until the collection and displayed invoice agree. This does not repair the existing per-page provenance or durable denial problems; it is held for review.

The first UI attempts failed before reaching the invoice book due to offscreen tap, then the corrected unchanged baseline reproduced a stale Show more control on the changed invoice (`/tmp/thorbis-invoice-replacement-red-scrolled.log`). A two-case run for the first gate passed (`/tmp/thorbis-invoice-replacement-green.log`), followed by a red for the missing refresh action (`/tmp/thorbis-invoice-refresh-red.log`). A DEBUG fixture simulated a changed invoice and job-list response; the subsequent three-case UI run passed replacement/refresh, estimate description and invoice signature navigation (`/tmp/thorbis-invoice-refresh-green.log`, matching before/after source hashes `/tmp/thorbis-invoice-refresh-green-{before,after}.sha`). This is a simulated response, not live authorization or actual offline fallback evidence.

A real-model gated URLProtocol test reproduced a dropped newer read after cancellation (`/tmp/thorbis-invoice-overlap-red.log`); a separate red showed a canceled newest waiter suppressing an earlier refresh (`/tmp/thorbis-invoice-cancel-newest-red.log`). The held model queue captures API generation on enqueue, retains valid older waiting reads across cancellation and coalesces only after completed results or definitive denials. Eight focused simulator tests passed (`/tmp/thorbis-invoice-queue-green.log`, matching before/after hashes `/tmp/thorbis-invoice-queue-green-{before,after}.sha`) covering both ordering cases, canceled waiter, multiple waiters, generation change, denial, an existing cancellation check and discounted amount. Several new tests were added without behavioral reds. This uses synthetic URLProtocol traffic; real server denial ordering, all session/authority switches, an actual offline fallback, invalid-amount UI and complete payment flow remain unverified. The model queue change affects all payment model consumers and requires independent review and additional offline/payment testing before release.
