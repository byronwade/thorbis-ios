# Job payment drafts, offline authority and in-flight work

Status: design investigation; no app, server, sync or storage behavior has changed. The held job-payment draft-cover experiment is not release-ready.

## Facts in the current code

- The API's assigned-work resolver checks the current tenant-matched invoice's `jobId`, the current job's assigned user, and that the job is not canceled. `packages/permissions/src/relationships.ts` says the assigned relationship is online-only for its evaluator; `services/api/src/composition/adapters.ts` resolves it against live data.
- The current PowerSync rules also expose an assigned-invoice projection keyed to a job-derived assignee and a bounded job window (`packages/sync-powersync/test/sync-rules.test.ts`, `contracts/sync/scopes.json`). This is a server-derived replication partition, not a statement that an offline device has learned about a reassignment made after it disconnected. The native iOS paths being investigated instead use `SavedCopies` and `JobDetailCache`, not that projection.
- The `/v1/query/catalog` binding's generation hashes tenant, actor, policy version and stream scope/window/team/location data (`packages/sync/src/scope.ts`). It does not hash each job assignment. iOS `SessionSnapshot` stores capability names, feature decisions and that binding; it does not contain an exact authorized job/invoice relationship. A matching generation or no-op foreground revalidation is therefore not proof that one invoice remains assigned.
- `invoice.view` is `allowed_with_snapshot`, while `invoice.payment.create` is `online_required`; the sync contract also lists `payments.record` as online-only. The existing iOS outbox separately saves locally observed cash/check receipt intent and sends it to the normal server endpoint when connected. This is not evidence that an invoice is paid: the server checks current authority and balance and may refuse it. Whether this local capture is covered by the canonical offline authorization contract requires domain reconciliation; do not call a provisional local record a server payment or silently redefine the existing capability.
- Cash/check recording persists an idempotency key in `InvoicePaymentIntentStore` before sending; the outbox preserves its key when offline. Tap to Pay has an in-memory controller/intent and distinct preparing, reader, processing and reconciliation phases; its cancellation currently returns the controller to idle. Link creation has a separate sheet-local busy flag. A privacy cover alone does not prove these operations stopped or that an interrupted card was not charged.

## Narrow implementation sequence

1. Preserve the already supported, released behavior while building and qualifying the replacement. Do not wire the held live-only cover or globally discard cached invoices, pending payment keys or outbox entries. Keep the user's editable amount and method in an invoice/actor/workspace-bound presentation draft, and keep active payment operations in an owner whose lifetime is not the sheet's. Scope or identity change may hide the draft, but must not discard or replay payment work under a different identity.
2. Add an explicit operation lifecycle with separate states for unsent draft, local cash/check receipt awaiting server, request in flight, provider result unknown, confirmed provider result awaiting webhook, and server-recorded receipt. Expose one read-only busy/uncertain state to the sheet and its authority gate. Do not automatically cancel, retry, or convert an unknown card/link/cash attempt on sheet dismissal. Preserve the exact existing request key, actor, workspace, invoice and payload, and use the existing server endpoint's authorization/idempotency checks on recovery. Provider-specific cancellation and terminal callback semantics must be proven against the actual Stripe implementation before a cancellation can mean no charge.
3. Specify a separate, versioned authorization envelope for each eligible offline read, produced inside the authenticated tenant transaction from the exact invoice, job/customer relation and current assigned-work policy. Bind actor, tenant, origin, job, invoice, resource revision, policy/scope generation, issuance/expiry, and digest of the exact stored response; bind any payment-history evidence separately and only after the server authorizes it. Authenticate its integrity with a platform/server-owned mechanism and protect its cache with the documented durable, cancellation and scoped-writer requirements. Explicitly define whether issuer permits bounded stale assignment evidence; a device offline cannot receive a remote revocation immediately, regardless of signature or expiry. The current assigned relationship contract fails closed, so introducing a bounded stale lease requires an explicit canonical contract, not a client-side assumption.
4. Migrate without breaking already supported field work: operate the envelope and verifier in shadow mode first; compare its decisions and expiry with real scoped reads without exposing customer data in logs, and measure both false holds and stale authorization. Preserve pending outbox records and their idempotency keys. Do not bless legacy unscoped files merely because they decode. A targeted migration must identify the verified actor/workspace/origin/resource relation or retain the legacy path until a supported replacement exists.
5. Only after the above contract and lifecycle are proven, make foreground revalidation leave the sheet's draft mounted behind an inaccessible cover, hide previous resource data and disable new actions until the exact resource has been reauthorized; resume the same draft after a safe decision. Revalidation with no signal, expiry, later revocation, and in-flight/unknown payment must each have a truthful separate state. If offline authorization cannot be proven under the adopted contract, keep the candidate held; do not claim both immediate revocation and unbounded disconnected operation.

## Required evidence before wiring

- Real iOS request/callback tests: cancellation immediately before/after response; delayed 200 versus newer 403/404; origin/actor/workspace/scope ABA; complete paginated payment history; job reassignment, cancel, deletion, customer/invoice relation change; two mounted scenes and process relaunch.
- Fault-injected cache tests: original bytes cannot be reauthorized after a denied response or stale async write; every scoped reader and list participates; marker/write/rename/sync failures and crash boundaries fail safely; an unrelated authorized invoice and its offline work remain available. Verify actual iOS file protection and supported app/extension processes, not only a macOS harness.
- Financial lifecycle tests: cash and check queued once with stable keys across failure and relaunch; card confirmation and webhook settlement in both orders; cancellation before and after potential charge; link creation with unknown outcome; no duplicate charge, unapproved new attempt or lost intent. Test on supported real devices for Tap to Pay.
- Mounted tests: enter a partial amount, perform no-op foreground revalidation, and retain it; observe denied/changed scope with no stale visible or accessible values; retry a failed fresh read without losing the draft; exercise no-signal and reconnect cases under the adopted offline contract.

The server separately mitigates duplicate attempts: `prepareInvoiceCardPresentIntent` reuses a matching replayable active attempt and rejects incompatible or already-processing ones. A fresh run of `pnpm --filter @thorbis/payments exec vitest run test/card-present.test.ts` passed all 12 tests, including replay, cross-method holds and callback settlement. These server tests do not prove the client SDK's cancellation timing or restart reconciliation, and cancellation must still not be described as proof that no charge occurred.
