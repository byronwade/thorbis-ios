# Held job invoice description reader — 3 November 2026

Status: test fixture only; no production reader implementation. Base: release commit `4012162`.

A technician can expand each invoice's item list on the job, but `JobInvoiceLineRows` truncates descriptions to two lines at normal text and expands them unbounded at accessibility sizes. The desired change is a bounded preview with Show more opening the full-height description, while preserving quantity, amount, invoice navigation and collection actions. A focused simulator test was prepared. Its baseline run `/tmp/thorbis-job-invoice-description-red.log` was stopped before the first assertion when free disk dropped to around 1.1 GiB (then 296 MiB); it is not a red behavioral result.

The existing customer-facing `ReadOnlyDocumentDescription` supplies a native sheet and session checks, but the job's invoice collection does not carry the actor, authority revision, API origin and request generation under which it was fetched. Additionally, the legacy 404/405 fallback currently treats organization-list and per-invoice records as fresh without checking whether they came from saved copies. A path-level `savedCopyDate` check after the fact is insufficient: `fieldInvoices()` fetches multiple pages, and a later live page clears a saved-copy marker for that path. The reader must not claim freshly authorized source data from these signals.

Before implementation, establish provenance for every relevant page and document, order late denial/refresh results, close the sheet on scope or document changes, retain ordinary offline behavior and prove scope/retry paths. The invoice itself and existing disclosure remain unchanged. No TestFlight or security-fix claim is made here.

Three transport-backed tests are staged in `JobCommercialDocumentsTests`: a job-invoice read mixing a saved page with a later live page; a legacy organization invoice read with the same mixture; and a saved per-ID invoice in legacy recovery. All expect offline records to remain visible and not become fresh. They have not run because disk space remains volatile and simulator use is held. The proposed fix needs a per-response provenance value and actual network validation (ordinary URLSession protocol-cache responses cannot establish freshness), aggregated over every page, plus a reader grant bound to the exact invoice and current identity. Replacements must invalidate that grant unless independently verified. These are design requirements, not verified behavior.

A separate, disconnected in-memory provenance primitive is staged in `InvoiceReadProvenance.swift`. It requires a complete ordered cursor chain marked network-validated, an exact current actor/tenant/job/customer/session/authority/transport scope, and the same invoice content digest. A pending same-resource denial retires a newer grant; a denial with no current scope retires the grant. It stores no invoice text. Lightweight macOS Swift harness `scripts/tests/invoice-read-provenance.swift` passed `/tmp/thorbis-invoice-provenance-final.log`; exact source hashes are `/tmp/thorbis-invoice-provenance-final-hashes.log`. The original intentionally incomplete model failed `/tmp/thorbis-invoice-provenance-red.log`. The terminal-cursor edge case failed `/tmp/thorbis-invoice-provenance-extra-red.log` and passed `/tmp/thorbis-invoice-provenance-extra-green.log`; missing-current-scope denial failed `/tmp/thorbis-invoice-provenance-scope-red.log` and passed `/tmp/thorbis-invoice-provenance-scope-green.log`.

This model is not wired to a transport, collection or view. Its page source, cursor chain, invoice digests and authorization are caller-supplied claims, not proven by the model; it is process-local and provides no durable denial or cross-process guarantees. It has not been built or tested in the iOS app. The three transport-backed XCTest cases and drawer UI test remain unrun. No user-facing feature, offline guarantee or security fix is claimed.

Independent review found that canceling a ticket immediately discarded its identity, allowing a late denial from an unfinished transport to leave a newer grant intact. The focused regression failed `/tmp/thorbis-invoice-provenance-cancel-red.log` and passed `/tmp/thorbis-invoice-provenance-cancel-green.log`. The held model now retains canceled tickets until an observed terminal response or explicit `finishCanceled`, which callers may use only after transport termination and after handling any denial. Exact source hashes: `/tmp/thorbis-invoice-provenance-cancel-hashes.log`. This only models the ordering contract: URLSession cancellation and terminal callback behavior, bounded cleanup in the real integration, durable denial and cross-process behavior are unverified.

A further review found that a canceled `publish` removed the ticket before checking cancellation. The new regression failed `/tmp/thorbis-invoice-provenance-canceled-publish-red.log` and passed `/tmp/thorbis-invoice-provenance-canceled-publish-green.log`. Additional lightweight regressions showed that a rejected partial publish and a first child denial could similarly retire observation before a later child denial (`/tmp/thorbis-invoice-provenance-partial-red.log`, `/tmp/thorbis-invoice-provenance-multidenial-red.log`). The held model now retains canceled, rejected and denied tickets, rejects publication unless the caller asserts every child request is terminal, and requires explicit terminal cleanup. Final standalone run `/tmp/thorbis-invoice-provenance-terminal-green.log`; source hashes `/tmp/thorbis-invoice-provenance-terminal-hashes.log`. The assertion is supplied by the caller and does not prove transport termination. Pending tickets can accumulate if integration fails to report completion; lifecycle and bounded cleanup are release prerequisites, as are URLSession behavior, durable denial, scope authorization and actual page/digest provenance.

Independent review of `66871bd` found no additional confirmed model defect and asked for a clearer caller contract. `allRequestsTerminal`, `finishCanceled` and `finishWithoutGrant` now explicitly require every child transport to be terminal and every denial callback delivered, not just a cancellation request. Standalone rerun `/tmp/thorbis-invoice-provenance-reviewed.log`; hashes `/tmp/thorbis-invoice-provenance-reviewed-hashes.log`. This is a clarification of a caller assertion, not verified URLSession behavior.

Transport review found that `APIClient.sendData` calls `Task.checkCancellation()` after `URLSession.data(for:)` and before reading HTTP status. A canceled request therefore cannot guarantee observation of an already-returned denial. The model now treats every unresolved same-actor, tenant, origin and job request as a barrier: a read started while another is pending is permanently ineligible to publish, even after the earlier request terminates. Only a new live read started after all same-resource requests have definitively terminated can grant access. This is conservative and affects the held model only; existing offline display remains unchanged. The initial cancellation barrier regression failed `/tmp/thorbis-invoice-provenance-barrier-red.log`; the stronger barrier harness passed `/tmp/thorbis-invoice-provenance-barrier-green.log`, hashes `/tmp/thorbis-invoice-provenance-barrier-hashes.log`.

The transport has not been instrumented: actual terminal callbacks, cancellation, error/status observation, per-page network-versus-saved-copy evidence and resource authorization are not established. Callers must not release a barrier until every underlying request and denial callback is terminal; a permanently hung transport can conservatively block a grant. The model remains process-local, does not provide durable revocation, is not wired to the drawer or any production read, and has no simulator/device coverage.

A lightweight macOS URLSession experiment (`scripts/tests/urlsession-cancel-observation.swift`) receives a stubbed HTTP 403, pauses immediately after `data(for:)` returns, cancels the task, then performs the app's `Task.checkCancellation()` before status inspection. It reports cancellation instead of the 403 (`/tmp/thorbis-urlsession-cancel-observation.log`; source hash `/tmp/thorbis-urlsession-cancel-observation-hash.log`). The first compiler invocation omitted `-parse-as-library` and did not run the experiment; the recorded successful invocation used it. This demonstrates the ordering on macOS with an injected response, not actual iOS URLSession cancellation timing, a real server, saved-copy provenance or the app's full transport.

Proposed transport integration (not implemented): add a narrowly scoped invoice GET variant that returns decoded value plus per-response provenance, uses a local URLCache-bypassing request policy and no-cache request header, bypasses `recentReads`, yet retains the existing scoped saved-copy fallback for offline display. It must tag saved copies at the actual return site, including both `knownOffline` and connection-error paths, rather than infer source from `savedCopyPaths`; each cursor page and each legacy per-ID fetch must carry its own source. Pagination must preserve page order, reject duplicate/empty cursors and report any cached page. Exact invoice snapshots/digests and actor, organization, customer, job, session, authority and API origin/generation must be bound at publication; a replacement must invalidate or independently re-establish that binding. Avoid changing unrelated `send` consumers or removing offline records.

Cancellation must be treated as an uncertain request outcome; the barrier may be released only after every underlying operation and denial callback is definitively terminal. Then a new, non-overlapping live read is required. The existing generic task-cancellation behavior alone does not establish this, and `URLSession`/HTTP cache policy is not proof of a correctly behaving intermediary or remote authorization while offline. Instrumentation must test real APIClient cache bypass, both saved-copy routes, mixed page orders, repeated/late denials, replacement and scope changes before this design is wired to any screen.

A disconnected transport prototype (`InvoiceResponseTransport.swift`) and local URLSession/URLProtocol harness (`scripts/tests/invoice-response-transport.swift`) are staged. The harness first failed against a placeholder (`/tmp/thorbis-invoice-response-red.log`) and passed the implementation (`/tmp/thorbis-invoice-response-green.log`; source hashes `/tmp/thorbis-invoice-response-hashes.log`). It checks network vs saved-copy labels, known-offline and connection-failure saved fallback, request cache settings, 403 rejection, changed final response URL and cancellation. The first attempt's test fixture hung before its cancellation gate because the placeholder never entered the network closure; that owned process was terminated, the fixture was corrected, and the recorded red was run afterward.

The component is not called by APIClient or the UI. The network and saved-copy closures are caller-supplied; they must be tied to the actual authenticated request and exact actor/tenant/origin/path/cursor. A final-URL check occurs after any redirect and does not prove credentials were not forwarded; integration must prevent unsafe redirects. Request cache settings do not prove remote intermediary behavior. Response-source labels alone do not establish current authorization, job membership, multi-page completeness, terminal ordering or durability. The harness uses macOS and synthetic responses, not an iOS device, real server, real saved-copy store or full app transport.

Independent review found that the prototype accepted HTTP 206 and caller-supplied Range/conditional headers, allowing a partial response to be mislabeled as a complete network read. The regression failed `/tmp/thorbis-invoice-response-content-range-red.log` (including a 200 response carrying Content-Range) and passed `/tmp/thorbis-invoice-response-partial-green.log`. The held helper now rejects Range, If-Range and conditional request headers, requires HTTP 200, and rejects Content-Range; exact source hashes `/tmp/thorbis-invoice-response-partial-hashes.log`. Its offline fallback remains unchanged. A 200 response and cache policy alone are not proof of complete semantic data, trusted intermediaries, safe redirects or authorized membership; JSON decoding, cursor and scope qualification remain caller obligations.

Per-page decoding is not aggregate completeness, and cancellation can still hide an HTTP status; the held barrier is not wired to these calls.
