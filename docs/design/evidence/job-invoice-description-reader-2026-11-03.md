# Held job invoice description reader — 3 November 2026

Status: test fixture only; no production reader implementation. Base: release commit `4012162`.

A technician can expand each invoice's item list on the job, but `JobInvoiceLineRows` truncates descriptions to two lines at normal text and expands them unbounded at accessibility sizes. The desired change is a bounded preview with Show more opening the full-height description, while preserving quantity, amount, invoice navigation and collection actions. A focused simulator test was prepared. Its baseline run `/tmp/thorbis-job-invoice-description-red.log` was stopped before the first assertion when free disk dropped to around 1.1 GiB (then 296 MiB); it is not a red behavioral result.

The existing customer-facing `ReadOnlyDocumentDescription` supplies a native sheet and session checks, but the job's invoice collection does not carry the actor, authority revision, API origin and request generation under which it was fetched. Additionally, the legacy 404/405 fallback currently treats organization-list and per-invoice records as fresh without checking whether they came from saved copies. A path-level `savedCopyDate` check after the fact is insufficient: `fieldInvoices()` fetches multiple pages, and a later live page clears a saved-copy marker for that path. The reader must not claim freshly authorized source data from these signals.

Before implementation, establish provenance for every relevant page and document, order late denial/refresh results, close the sheet on scope or document changes, retain ordinary offline behavior and prove scope/retry paths. The invoice itself and existing disclosure remain unchanged. No TestFlight or security-fix claim is made here.

Three transport-backed tests are staged in `JobCommercialDocumentsTests`: a job-invoice read mixing a saved page with a later live page; a legacy organization invoice read with the same mixture; and a saved per-ID invoice in legacy recovery. All expect offline records to remain visible and not become fresh. They have not run because disk space remains volatile and simulator use is held. The proposed fix needs a per-response provenance value and actual network validation (ordinary URLSession protocol-cache responses cannot establish freshness), aggregated over every page, plus a reader grant bound to the exact invoice and current identity. Replacements must invalidate that grant unless independently verified. These are design requirements, not verified behavior.

A separate, disconnected in-memory provenance primitive is staged in `InvoiceReadProvenance.swift`. It requires a complete ordered cursor chain marked network-validated, an exact current actor/tenant/job/customer/session/authority/transport scope, and the same invoice content digest. A pending same-resource denial retires a newer grant; a denial with no current scope retires the grant. It stores no invoice text. Lightweight macOS Swift harness `scripts/tests/invoice-read-provenance.swift` passed `/tmp/thorbis-invoice-provenance-final.log`; exact source hashes are `/tmp/thorbis-invoice-provenance-final-hashes.log`. The original intentionally incomplete model failed `/tmp/thorbis-invoice-provenance-red.log`. The terminal-cursor edge case failed `/tmp/thorbis-invoice-provenance-extra-red.log` and passed `/tmp/thorbis-invoice-provenance-extra-green.log`; missing-current-scope denial failed `/tmp/thorbis-invoice-provenance-scope-red.log` and passed `/tmp/thorbis-invoice-provenance-scope-green.log`.

This model is not wired to a transport, collection or view. Its page source, cursor chain, invoice digests and authorization are caller-supplied claims, not proven by the model; it is process-local and provides no durable denial or cross-process guarantees. It has not been built or tested in the iOS app. The three transport-backed XCTest cases and drawer UI test remain unrun. No user-facing feature, offline guarantee or security fix is claimed.

Independent review found that canceling a ticket immediately discarded its identity, allowing a late denial from an unfinished transport to leave a newer grant intact. The focused regression failed `/tmp/thorbis-invoice-provenance-cancel-red.log` and passed `/tmp/thorbis-invoice-provenance-cancel-green.log`. The held model now retains canceled tickets until an observed terminal response or explicit `finishCanceled`, which callers may use only after transport termination and after handling any denial. Exact source hashes: `/tmp/thorbis-invoice-provenance-cancel-hashes.log`. This only models the ordering contract: URLSession cancellation and terminal callback behavior, bounded cleanup in the real integration, durable denial and cross-process behavior are unverified.

A further review found that a canceled `publish` removed the ticket before checking cancellation. The new regression failed `/tmp/thorbis-invoice-provenance-canceled-publish-red.log` and passed `/tmp/thorbis-invoice-provenance-canceled-publish-green.log`. Additional lightweight regressions showed that a rejected partial publish and a first child denial could similarly retire observation before a later child denial (`/tmp/thorbis-invoice-provenance-partial-red.log`, `/tmp/thorbis-invoice-provenance-multidenial-red.log`). The held model now retains canceled, rejected and denied tickets, rejects publication unless the caller asserts every child request is terminal, and requires explicit terminal cleanup. Final standalone run `/tmp/thorbis-invoice-provenance-terminal-green.log`; source hashes `/tmp/thorbis-invoice-provenance-terminal-hashes.log`. The assertion is supplied by the caller and does not prove transport termination. Pending tickets can accumulate if integration fails to report completion; lifecycle and bounded cleanup are release prerequisites, as are URLSession behavior, durable denial, scope authorization and actual page/digest provenance.
