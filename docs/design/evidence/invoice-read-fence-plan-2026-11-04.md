# Held invoice denial fence

Customer document and staff invoice/payment readers need a durable, resource-specific denial that survives restart without losing offline cash/check intents. Existing `SavedCopyStore` keeps invoice detail and list JSON by actor/workspace and origin-keyed read; `JobDetailCache` independently stores invoice, payment and job-list copies by ID. Closeout and other views also consume those copies. None is currently bound to a durable per-invoice denial, and queued asynchronous reads can write after a denial. The outbox and payment intent store must not be erased.

This isolated first slice is a held, unwired transport-fence primitive, not a user-facing privacy fix. It uses actor/workspace/origin/invoice/resource-specific identity. Before a live request starts it must durably publish a hold. An OS-backed per-scope lease remains held until all response status/denial callbacks are delivered. Overlapping requests cannot authorize old cache; only a new complete live attempt begun after all earlier leases are gone may clear the hold. A connectivity failure may restore a previously verified offline grant only when that attempt was isolated and no other observation changed its epoch. A crash or interrupted attempt remains held. Persistence and lock errors must fail closed. Invoice and payment history have separate resource scopes.

The primitive does not establish that the caller's result was actually live or complete; the caller must supply that proof and keep a lease through terminal response handling. It does not invalidate already-rendered views, saved lists, unscoped caches or cross-process observers. The held scope is not yet wired to API reads, mutation responses, session/auth changes, sign-out, customer pages, payments, closeout, or legacy-cache migration. Authority snapshots and offline revocation limits remain unresolved. No production feature should use it until a single owner mediates all those paths, a durable scope/authority proof is verified, and device/relaunch, failure, denial, identity, concurrency and offline/outbox behavior are tested. In particular, old unscoped copies cannot be presumed authorized by a newly created grant.

## Prototype evidence and limits

The held primitive serializes live requests for the same actor, organization, origin, invoice and resource with a continuous exclusive filesystem lease. A second request is refused before it can start; a future production owner would need to coalesce or retry it. Every accepted attempt persists a pending marker before transport, and a crash leaves that marker held. Isolated connectivity failures can restore the exact prior clean epoch. Denial or write failure leaves a hold; only a subsequent isolated, complete live read may clear it. Payment-history cache additionally requires its parent invoice's verified epoch: a pending or denied invoice blocks history, and a fresh invoice verification changes the epoch so previously saved history must be reverified. A history denial does not itself retire the invoice.

An intentionally abandoned attempt retains its open lease until process exit, because dropping the Swift object does not prove its transport stopped. This is an availability and resource-leak tradeoff, not a production-ready lifecycle. The directory and lock files must never be removed or replaced while attempts can run, including at sign-out. The API does not track or observe already-mounted views and cannot stop a separate consumer from reading existing cache files. A process-wide notification/lifecycle owner, cross-process observation or an enforceable cache-access lease, sign-out fencing and complete response provenance remain necessary. The prototype accepts only UUID-shaped identity fields; real session ID shapes and canonical origin mapping have not been qualified. Its unprotected marker contains only digests and status, but corruption, directory substitution, data protection, hostile filesystem changes, backup/restore and hardware power loss are not qualified. The full-ledger/authority and offline-expiry problem remains open, and a new marker cannot validate a legacy unscoped cache.

The standalone macOS harness at `tools/held-invoice-fence/run.sh` passes (`/tmp/thorbis-invoice-fence-final-verified.log`); its source hashes match `/tmp/thorbis-invoice-fence-final-before.sha` and `-after.sha`. It exercises real filesystem locks, fresh/denied/offline paths, failed denial persistence via a read-only directory, a child process terminating after preflight, competing processes, parent invoice/history dependency, actor/workspace/origin isolation, and an abandoned lease. The earlier tests demonstrated red states for initial unverified cache, overlapping transport, dropped attempt and parent denial (`/tmp/thorbis-invoice-fence-red.log`, `-serial-red.log`, `-drop-red.log`, `-parent-red.log`). This is a macOS process/permission experiment, not iOS simulator/device, full app, power-loss or integration qualification. No user-visible UI, pending intents, outbox or existing cache code changed.

## Completion result follow-up

`finish` returns `committed`, `held`, or `denied` explicitly; stale or missing pending metadata and a denied or changed parent invoice return `held`. The standalone harness exercises both parent races, missing pending metadata, a committed live read, and denial. A committed result describes a durable ledger transition at that instant only. It is not a presentation lease: a later concurrent denial may retire it before a caller publishes content. Atomic publication and visible cross-process retirement remain unimplemented, as do actual app transport and cache integration. This candidate remains disconnected.

The targeted regression failed before the result change (`/tmp/thorbis-invoice-fence-finish-red.log`). The final standalone run passed (`/tmp/thorbis-invoice-fence-finish-final.log`), with matching before/after source manifests (`/tmp/thorbis-invoice-fence-finish-before.sha` and `/tmp/thorbis-invoice-fence-finish-after.sha`). This is not an iOS or end-to-end app test.

## Held cache-write experiment

The disconnected `withCacheWrite` experiment checks the current clean invoice and parent epoch under the metadata locks, durably writes a pending hold, invokes a synchronous write, then restores the prior clean record. Cooperating process preflight cannot enter while that closure holds the lock. A caller-supplied closure must itself do an atomic durable replacement, must not reenter the fence, and must not publish UI. A simulated write failure leaves the pending hold in the tested path. `/tmp/thorbis-invoice-publication-red.log` reproduces using a prior check after a second process denies; `/tmp/thorbis-invoice-publication-final.log` passes the held-then-deny, in-lock cross-process contention, success and injected closure-failure scenarios. Before/after source manifests are `/tmp/thorbis-invoice-publication-before.sha` and `-after.sha`.

This is not a complete production cache or presentation solution. The write and the final marker are separate filesystem operations; if the final marker rename succeeds but directory fsync reports failure, its visibility/durability is uncertain and this prototype has no cross-process poison barrier. No actual cache writer, transport response, saved-copy list, outbox, session lifecycle or UI is wired; existing asynchronous cache writers can bypass it. It cannot itself revoke an already displayed screen or protect a later display after the lock is released. Live response publication must coordinate with the pending transport attempt rather than calling this clean-only helper. Scope identity, actual iOS storage, crash/power-loss and broader offline behavior remain unqualified. Do not enable it in the app.

## Exact-read publication receipt

The held cache-write operation now requires a receipt returned under the metadata lock by the corresponding committed read. It checks the hashed resource identity, exact read epoch and parent invoice epoch before entering the write closure. The harness reproduces the former check-only ABA: a read A, denial and fresh read B allowed an old write (`/tmp/thorbis-invoice-publication-aba-red.log`). The final test also rejects an old history receipt after its parent and history epochs change, and rejects using a receipt for another invoice.

This receipt is metadata, not proof that the supplied bytes came from that response; an eventual trusted transport/cache owner must bind immutable bytes to it, handle retries and write ordering, and preserve the existing offline data path. It does not manage visible UI, prevent nonparticipating writers, or solve final-marker rename/fsync ambiguity. The component remains disconnected and unqualified for production.

## Payload and offline-restoration receipts

The live completion now hashes the supplied response bytes into its receipt, and the held cache-write operation checks the supplied bytes against that digest and passes those same bytes to the trusted writer. A connectivity failure that restores a previously clean offline state returns `.restored` without a live-write receipt. The former behaviors were reproduced as failing assertions in `/tmp/thorbis-invoice-receipt-offline-red.log` and `/tmp/thorbis-invoice-receipt-payload-red.log`. The final standalone harness tests both, alongside the earlier epoch and cross-process cases.

This is still an untrusted caller contract: the transport must provide the true complete response, and the writer must atomically and durably store exactly the bytes it receives. The digest does not establish server authorization, response freshness or semantic completeness. Actual UI retirement, cache migration, final-marker fsync error and end-to-end offline behavior remain open. No production path is wired.

## Version-bound cached bytes

The held clean ledger records the digest of the exact successful response. Cache checks require the actual cached bytes and compare their digest with that ledger; connectivity restoration retains the prior digest, and missing legacy digests fail closed. The harness reproduces A cached → denial → B live → A read before B installation in `/tmp/thorbis-invoice-bound-cache-red.log`. The final harness uses an actual temporary cache file for A and B, verifies the old bytes are rejected and installed B accepted, injects a failure after replacement, and exits a child process inside the write closure; the latter two leave the scope held in this experiment.

This version check depends on every real reader hashing the exact bytes it actually reads and every writer cooperating. It does not protect a check followed by a later uncoordinated UI publication or revoke already-visible content. The sample atomic writer does not qualify the app's actual storage, iOS file protection, power-loss behavior, final-marker rename/fsync failure, transport authority, logout or offline migration. No existing cache, outbox or UI has been changed; this remains held.
