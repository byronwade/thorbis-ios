# Customer record loading: bounded job reads

This worktree is not release-qualified. Customer profile compilation previously waited for each job's notes, media, estimate links and invoices sequentially, then separately waited for each job's legacy photos. The candidate uses at most four concurrent per-job sequences for profiles with three or more jobs and merges in the original job order. Each job retains its existing request order, media failure and archived-photo fallback rules. API request-generation changes cancel the whole compilation. This is bounded concurrency, not demand paging: all authorized jobs and their records are still read.

A standalone Swift 6 harness compiled the actual `CustomerJobCompilation.swift` with a deterministic, actor-isolated fake API. Six jobs with delayed notes produced `peak=1` and failed the desired overlap assertion on the unmodified release source; the candidate produced `peak=4` and retained the job-group order. Separate runs confirmed foreign notes are excluded, failed media is marked incomplete, and both task cancellation and an API-generation change cancel the compilation. Commands and harnesses used `/tmp/customer-scaling-harness.swift`, `/tmp/customer-scaling-partial.swift`, `/tmp/customer-scaling-generation.swift`, `/tmp/customer-scaling-cancel.swift` and `swiftc -swift-version 6 -parse-as-library`; these are synthetic observations, not real-device latency measurements.

Request-keyed app XCTest coverage was added for bounded overlap, ordering, foreign data, media failure, 401 and generation change. The fixture compiles independently under Swift 6; the app and XCTest suite have not yet been built or run. Simulator access is held for TestFlight work. No claim of app-level, network, physical-device or release verification is made.

An initial iPhone simulator run passed 34 focused tests (five new concurrency cases, 20 existing customer compilation cases and nine What's New cases), log `/tmp/thorbis-customer-loading-test.log`. Independent review then requested more financial, out-of-order and authority-retirement coverage. The candidate was subsequently changed to check a captured customer/session/policy scope between reads, and additional request-keyed cases were added. The 34-test result predates those source changes; the final candidate still requires a fresh app build and rerun.

Authority checks fence each customer compilation page before and after its request; they do not fence `APIClient.sendData`'s existing saved-copy write, which may occur before a retired-policy response is rejected by the caller. That pre-existing cache-policy issue requires separate review. In the checked backend source, contacts, locations, job notes and legacy photos return whole arrays and their repositories do not apply a page limit. The iOS helpers decode a `FieldPage` but ignore any `nextCursor`, so a future paginated version of those endpoints would need explicit compatibility handling. Existing notes and legacy photo requests remain unpaged and can still be large.

The final candidate's iPhone simulator run passed 38 focused tests: nine request-keyed concurrency, authorization, pagination and financial tests; 20 existing customer compilation tests; and nine What's New tests. The app built as part of the run. The result is `/tmp/thorbis-customer-loading-derived/Logs/Test/Test-Thorbis-2026.11.03_01-10-42--0500.xcresult`; the log is `/tmp/thorbis-customer-loading-final.log`. Product and test file hashes matched before and after the run (`/tmp/thorbis-customer-loading-final-before.sha`, `/tmp/thorbis-customer-loading-final-after.sha`). The controlled pagination check against the extracted original paginator requested page 2 after authority retirement; the revised paginator stopped after page 1. This does not establish live-network speed, full-suite coverage, demand paging, physical-device behavior, or release status.
