# Proposed catalog keyboard layout

The current invoice search screen pins the search field and category chips above the scroll view. After adding a line, the selected-line disclosure is inserted before results. On the 375-point simulator in `obscured-result.png`, these occupy nearly all of the area above the keyboard and its accessory. The result is partly tappable but its price and Add label are concealed. The same test's `isHittable` assertion therefore does not establish that the action is understandable.

A candidate worth prototyping on the invoice surface:

1. While entering a search, offer the selected category in a clearly labeled native `Menu` beside the search field, with the existing category choices and selection preserved. It replaces the second chip row only in the keyboard-constrained search state. Return to the chips when space is available. Maintain a 44-point target and an accessible label naming the selected category; do not present an icon-only filter whose state is hidden.
2. Make the collapsed last-added disclosure a single compact, accessible row naming the edit action and the selected item's identity. Its summary and full description remain available when expanded. Do not put the disclosure after an arbitrarily long result list or silently dismiss the keyboard on each add.
3. Arrange an ordinary short catalog result so its kind, description, price, added quantity, and add action are legible with the row as one tap target. Long descriptions must remain readable in full by scrolling; an assertion that every possible row fits above a keyboard would be incorrect. Do not replace data with illustrations or hide line details.
4. When editing the selected line at accessibility sizes, give the editor enough vertical space by collapsing nonessential search chrome only if the search and category state remain preserved and there is a clearly labeled route back to results. Keep the editor inline if that can meet the same requirement without making controls unreachable. Retain all existing reorder, delete, reason and line fields.

Verification should use the short known fixture to check visible price and Add after one and repeated selections; separately exercise a long description and verify its complete text can be read, selected category visibility and changes, no-match custom-line creation, cancel/back, the expanded line editor, quantity and unit price at largest Dynamic Type, and estimate flows sharing the catalog component. Capture the actual normal and large-text screens above the keyboard and inspect them; `isHittable` alone is insufficient. VoiceOver and an actual device remain separate checks. The 44-point accessory offset in the experimental test must be confirmed against the observed keyboard geometry rather than assumed portable.

This is a proposal, not an implemented or verified change. It should be compared with the existing Paper design and checked against all callers before being selected.
