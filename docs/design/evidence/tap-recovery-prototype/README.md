# Tap recovery store prototype — not wired or release-ready

Base: iOS Tap reader isolation branch `9a4c96f`. The Tap build policy is unchanged and remains disabled. This store is not referenced by the app's payment controller, does not initiate payments, and is not a recovery feature.

The prototype stores stable origin, organization, actor, invoice, amount, currency and optional canonical attempt ID. It deliberately stores no client secret, card data, or SDK continuation. A hold without an ID represents a lost preparation response and cannot be resolved by the current read-only server API. A hold is only removed by an exact ID and amount/currency check, and the caller must independently establish a current authorized session and authoritative canonical receipt. Future integration must gate every payment effect on successful store writes, fail closed on inaccessible/corrupt storage, make receipt verification mandatory, and address termination at every boundary. This prototype does not establish crash/power-loss durability, physical-device behavior, production backend support, or entitlement/merchant readiness.

- `xcrun swiftc docs/design/evidence/tap-recovery-prototype/process-check.swift Thorbis/Sources/APIOrigin.swift Thorbis/Sources/TapRecoveryStore.swift -o /tmp/tap-recovery-process-check`, followed by `write` and `read` in two distinct executable invocations against the same temporary file, printed `hold restored in separate process`. This checks normal process restart, not crash or power loss.
- `ThorbisTests/TapRecoveryStoreTests.swift` was added but XCTest was not run; the simulator was not used.

Outstanding: use a reviewed durable storage protocol and canonical server lookup bound to the exact authenticated tenant, actor, job and invoice; qualify process termination, concurrent writers, protected-data behavior, storage errors, session revocation and receipt confirmation on device. A successful test of the standalone store is not evidence these properties hold in the app.

## Canonical identity follow-up

The store now accepts only UUID identities and origins accepted by the same shared `APIOrigin` trust policy used by `APIClient`. Organization, actor, invoice and attempt UUIDs are normalized before comparison or storage; accepted host case and root-slash variants use the same origin. Inaccessible, malformed, untrusted or duplicate-equivalent saved holds fail closed. The standalone alternate-representation test failed before this change and passed after; the check compiled and ran in both normal and `-D DEBUG` modes, including each mode's API origin policy. A separate-process restart check passed after the change. XCTest and the full app build have not run.

The prototype **still has no client operation ID**, no job binding and no production call sites. Before any integration, generate a UUID client operation ID and durably commit it with the canonical scope before the first preparation request; reuse that exact ID for the server's lookup and never infer a safe retry from an absent result. The server must derive the job from the authenticated invoice and authorize both; a local job ID may be a navigational consistency check but is never authority. Actor, organization, API origin and current session must be revalidated before lookup or receipt clearance, and the canonical attempt ID and exact verified receipt must be bound to that operation. The new backend operation contract is a separate unexposed prototype and is not yet a supported API. Storage crash/power-loss behavior, multi-process synchronization, cancellation, sign-out, revocation and legacy/format migration remain unqualified.
