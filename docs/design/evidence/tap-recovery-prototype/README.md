# Tap recovery store prototype — not wired or release-ready

Base: iOS Tap reader isolation branch `9a4c96f`. The Tap build policy is unchanged and remains disabled. This store is not referenced by the app's payment controller, does not initiate payments, and is not a recovery feature.

The prototype stores stable origin, organization, actor, invoice, locally observed job, generated operation ID, amount, currency and optional canonical attempt ID. It deliberately stores no client secret, card data, or SDK continuation. A hold without an ID represents a lost preparation response and cannot be resolved by the current read-only server API. A hold is only removed by an exact ID and amount/currency check, and the caller must independently establish a current authorized session and authoritative canonical receipt. Future integration must gate every payment effect on successful store writes, fail closed on inaccessible/corrupt storage, make receipt verification mandatory, and address termination at every boundary. This prototype does not establish crash/power-loss durability, physical-device behavior, production backend support, or entitlement/merchant readiness.

Outstanding: use a reviewed durable storage protocol and canonical server lookup bound to the exact authenticated tenant, actor, job and invoice; qualify process termination, concurrent writers, protected-data behavior, storage errors, session revocation and receipt confirmation on device. A successful test of the standalone store is not evidence these properties hold in the app.

## Canonical identity follow-up

The store now accepts only UUID identities and origins accepted by the same shared `APIOrigin` trust policy used by `APIClient`. Organization, actor, invoice and attempt UUIDs are normalized before comparison or storage; accepted host case and root-slash variants use the same origin. Inaccessible, malformed, untrusted or duplicate-equivalent saved holds fail closed. The standalone alternate-representation test failed before this change and passed after; the check compiled and ran in both normal and `-D DEBUG` modes, including each mode's API origin policy. A separate-process restart check passed after the change. XCTest and the full app build have not run.

The dark coordinator now generates and atomically writes a UUID operation ID and local job context before invoking an injected preparation transport, and never initiates another preparation for a held invoice. It has no production call sites. Before integration, qualify stronger durable storage semantics and reuse that exact ID for the server's lookup; never infer a safe retry from an absent result. The server must derive the job from the authenticated invoice and authorize both; a local job ID may be a navigational consistency check but is never authority. Actor, organization, API origin and current session must be revalidated before lookup or receipt clearance, and the canonical attempt ID and exact verified receipt must be bound to that operation. The new backend operation contract is a separate unexposed prototype: it has no HTTP route and its current status projection does not include the job/operation fields this coordinator expects, so the integration is not implemented. Storage crash/power-loss behavior, multi-process synchronization, cancellation, sign-out, revocation and legacy/format migration remain unqualified.

## Operation-identity coordinator follow-up

A standalone `coordinator-check.swift` drives a fake injected transport, not an API client or Stripe. In both normal and `-D DEBUG` compilation it passed scenarios for a failed store write before transport, unchanged or stale terms, lost preparation response, reopening with a saved hold, wrong actor, missing/error/pending lookup, wrong operation, job, amount or attempt, authorization loss during lookup, and an exact recorded response. A separate process read the saved generated operation and job after a normal writer exit. These checks do not prove crash or power-loss durability, actual session resolution, the authenticity of an injected status, app UI behavior, or provider settlement.

Existing pre-operation prototype files lacking the new required IDs fail closed on decode; no migration has been designed. Never wire this type to a payment UI until a reviewed, authenticated status contract verifies the exact server-derived job and receipt and the server and client agree on response shape. No live server, provider, simulator, XCTest or full app build was used.
