# Held durable invoice capture intent experiment

This branch is a storage-only prototype, not an editor integration or a releasable recovery feature. The prior in-memory receipt experiment allowed a writer to advance past a capture whose commit result was ambiguous. This experiment registers an exact scoped intent and encrypted payload in a separate SQLite transaction before capture, then keeps the intent in both registered and committed states. All operations using this version of the transaction fence reject an unresolved intent. No intent-clearing or reconciliation API exists; the state intentionally blocks indefinitely.

The `invoice_durable_intent_probe.swift` host run confirms two fence instances block capture, legacy save, begin and recovery while an intent is registered or committed; it also checks the earlier snapshot remains. The `invoice_durable_crash_probe.swift` host run kills separate processes after registration and after committed capture, and verifies another instance cannot advance or recover; two simultaneous processes racing to register admit exactly one. These are macOS host results with synthetic bytes, not iOS file-protection, power-failure, or security evidence. The API was compiled on host using Swift 6 and SQLite. The first test failed because the intent API did not exist before implementation.

Do not integrate: this is not compatible with old binaries or unfenced database writers; it has no authority/session/revision checks, full snapshot proof, observed-commit receipt, authorized reconciliation, owner transfer, disk-full proof, encryption/key management, or database/WAL protection. It stores an additional encrypted payload in the intent. A caller that cannot obtain a registration result cannot resolve it. Existing capture callers do not use the staged API. Crash before commit boundaries and transaction interruption remain to be tested. The host tests do not prove network freshness or financial mutation correctness.

Follow-up review found that the original experiment still exposed direct capture and legacy save, so same-version clients could bypass intent registration. A focused test first reproduced `unguarded capture allowed`. The experiment now fails both direct entry points closed; existing callers are therefore deliberately incompatible until redesigned. Host tests pass against registered and committed intents by attempting a second *intent registration*, rather than relying only on disabled legacy APIs. The read-only inspection returns encrypted evidence and distinguishes registered from committed across process death, while checking actor/customer/job metadata. That comparison is not authorization; it must not be exposed before a fresh authenticated, generation-checked invoice read and capability/revision checks. No resolution, deletion, or submission is provided. The inspected `InvoiceDraftRecoveryAccess` is a caller-provided collection of booleans, not a server-issued attestation; editor `reloadLatest` reads a live invoice but does not by itself provide full reconciliation authority.

## Held user-choice record

The prototype can record an explicitly supplied previous/candidate choice against an unresolved intent. An externally injected synchronous check is required but is not authenticated by this layer. Wrong scope, denied checks, unavailable prior snapshot and conflicting decision IDs fail; replay of the same ID and choice succeeds across instances, including after subprocess SIGKILL following decision commit. Both snapshots and the intent remain, so recovery, submission and new writes remain blocked. A focused regression also prevents the original capture from transitioning after a choice was recorded. This is a durable choice record only: it does not resolve the intent, prove user intent, enforce live authority, expose contents safely, or recover the editor. The injected check cannot atomically establish server authority, and its proper threading/lifetime are undecided. No pruning or deletion is performed.

**Independent review: unsafe as an authorization boundary.** Another instance that knows the stored IDs can call the inspection API to receive the raw payload and can pass `authorize: { true }` to commit the first choice; the resulting decision cannot currently be changed. A host reviewer reproduced both behaviors. The callback therefore does not prove current actor, tenant, consent, or session authority. Do not expose either inspection payloads or choice recording to the app until a trusted coordinator, actual encryption/key access, lifecycle-bound session checks, and a reversible, authenticated resolution protocol exist. The fence deliberately remains closed after a choice, including after crash. BEGIN IMMEDIATE serializes the tested choice and capture transaction; it does not establish user authority.
