# Customer location notes: focused reader candidate

The technician visits a customer, scans the service locations and needs to read a complete set of site instructions without a long note pushing every later location and section down the page. The requested first slice is a reader; it does not claim an editable canvas or durable draft recovery.

The current `CustomerDetailView.locationsSection` prints location notes in full. The existing `ServiceLocationSheet` edits all fields, and the existing Options menu must remain available. The candidate should show a labeled, two-line preview for long or multiline notes and a clearly labeled Show more action that presents the entire note in a large native sheet. Short notes remain fully visible. Keep address links, parking, dogs/hazards, map-pin state, all existing actions and roles. Long notes can contain important instructions: the preview and its action must clearly indicate that more text exists, never replace or hide the explicit hazard fields.

The existing customer page uses the app's own typography, semantic colors and native sheets. [Shopify's customer profile](https://mobbin.com/screens/eef0daad-490b-4e23-862c-2f97c11f1b6a?utm_source=chatgpt&utm_medium=ai-assistant&utm_source_platform=mcp) is one observed example of a distinct labeled note area and a direct edit action. It informs hierarchy, not Thorbis styling or behavior. The proposed compact preview and large reader are a Thorbis-specific adaptation for the user's long-content requirement; the existing document reader is a useful local interaction reference, not a suitable source of customer authorization.

Authority must bind the opening to the currently shown customer, location ID and unchanged note, active organization, signed-in actor, session generation, authority revision, and customer-view capability. Dismiss or blank the reader when any changes, and do not open or show another customer's record. No stale copied location object may reach an edit action. Offline viewing must keep the same scope and saved-copy rules as the current customer page. Keep editing in the current location sheet and retain the `customer.edit` capability check; a separate edit canvas or implicit draft preservation is outside this slice. If adding direct edit from the reader, transfer sheet presentation only after dismissal, re-resolve the current location and recheck permission/session before opening; otherwise retain the existing Options edit action.

The test fixture adds paragraphs through a DEBUG-only preview. The baseline verified the long location note existed, then failed on the missing reader action (`customer-location-notes-red-confirmed-1113.log`). An initial reader build passed two targeted iPhone tests for reading all notes and retaining the existing edit menu (`customer-location-reader-green-1113.log`). On a later source revision, a four-test run had two passes (largest text and a DEBUG session-expiration case) and two failures: the existing long-location label and menu were not hittable after upward-only scrolling, and the normal-text reader action was present but not hittable after upward-only scrolling (`customer-location-reader-scoped-green-1113.log`). Cause is not established. No completed post-change run covers all scenarios.

**Status: held, not release-ready.** After that run the tests changed to scroll based on element frame rather than only upward, and the source changed to tie the location-notes data to the session, API origin, request generation and saved-copy revision captured when the request began. The load task now restarts when this authority changes. These subsequent changes have not been built or run. The change must not hide legitimate offline-authorized notes merely because a network request fails; actual saved-copy behavior after authority revalidation remains unverified. The original editor/handoff and discard experiment is separately preserved in `/Users/byronwade/testflight-work/customer-location-editor-held-1113.patch`; it is not part of this branch. It does not solve root-replacement draft loss or prove safe response identity and must not be shipped as-is.
