# Held job-estimate draft release integration

This candidate is based on release commit `4012162`. The release did not contain the previously held local commercial-draft foundation. The estimate-only subset was ported from the held recovery branch, and the job draft save/close safeguard was applied without the disconnected atomic command or invoice-editor integration. Job-bound creation remains available.

The first-link path now performs a fresh estimate and job read and compares the saved estimate terms, scope, relationship, and permissions before invoking the legacy link endpoint. This is not an atomic revision precondition: the estimate, relationship, policy, or authorization can change after the check and before link. The legacy create lacks a durable server idempotency key. The client persists an uncertain-create hold before sending, but cannot guarantee recovery if local persistence, process termination, or old/uncoordinated writers defeat it. This candidate is held for independent review and backend-qualified atomic command; do not describe financial safety as solved.

A UI behavioral baseline before the first-link change observed `creates=1,links=1,estimateReads=0,jobReads=0` against a changed-estimate fixture (`/tmp/thorbis-initial-link-red2.log`). Xcode test results and source hashes for the integrated final source must be recorded separately. The earlier post-create sheet tests passed only on the held parent branch (`/tmp/thorbis-job-exit-actual-job.log`) and do not establish this integration works. An earlier integration compile failed because the port initially lacked the debug write-injection argument (`/tmp/thorbis-job-exit-release-xcode.log`); the argument was added before the baseline was rebuilt.

A failed final write on parent-driven view removal can still release the draft owner while in-memory edits are lost. Actual actor/workspace changes, session transitions, errors after writes, old writers, power loss, and device file protection require additional work and qualification. Long-description support remains capability gated and requires the separately held backend; it has not been enabled by this change.
