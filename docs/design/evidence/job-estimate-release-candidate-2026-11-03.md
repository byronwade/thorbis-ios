# Held job-estimate draft release integration

This candidate is based on release commit `4012162`. The release did not contain the previously held local commercial-draft foundation. The estimate-only subset was ported from the held recovery branch, and the job draft save/close safeguard was applied without the disconnected atomic command or invoice-editor integration. Job-bound creation remains available.

The first-link path now performs a fresh estimate and job read and compares the saved estimate terms, scope, relationship, and permissions before invoking the legacy link endpoint. This is not an atomic revision precondition: the estimate, relationship, policy, or authorization can change after the check and before link. The legacy create lacks a durable server idempotency key. The client persists an uncertain-create hold before sending, but cannot guarantee recovery if local persistence, process termination, or old/uncoordinated writers defeat it. This candidate is held for independent review and backend-qualified atomic command; do not describe financial safety as solved.

A UI behavioral baseline before the first-link change observed `creates=1,links=1,estimateReads=0,jobReads=0` against a changed-estimate fixture (`/tmp/thorbis-initial-link-red2.log`). Xcode test results and source hashes for the integrated final source must be recorded separately. The earlier post-create sheet tests passed only on the held parent branch (`/tmp/thorbis-job-exit-actual-job.log`) and do not establish this integration works. An earlier integration compile failed because the port initially lacked the debug write-injection argument (`/tmp/thorbis-job-exit-release-xcode.log`); the argument was added before the baseline was rebuilt.

A failed final write on parent-driven view removal can still release the draft owner while in-memory edits are lost. Actual actor/workspace changes, session transitions, errors after writes, old writers, power loss, and device file protection require additional work and qualification. Long-description support remains capability gated and requires the separately held backend; it has not been enabled by this change.

On exact source commit `46333eb`, the release-based simulator suite compiled and passed 20 unit checks and five UI checks: actual job-sheet post-create failure/close, controlled transport-generation recovery and original-scope reopen, changed estimate and changed job before first link, and unchanged job/estimate link. The sixth UI case initially failed because its assertion prohibited the expected fresh access-verification reads on reopen even though the observed counters showed no create or link (`/tmp/thorbis-job-exit-release-green.log`, hashes `/tmp/thorbis-job-exit-release-green-hashes.txt`). The test-only follow-up distinguishes verification reads from automatic writes, and its focused rerun passed (`/tmp/thorbis-job-exit-interrupted-retry.log`), including an explicit retry of the same saved estimate. The original failing suite remains a failure; the focused rerun is separate evidence. The simulated generation invalidation is not a real actor/workspace change, and the sheet drag does not independently prove that iOS began an interactive transition. The production source was unchanged between these two runs.

## Held parent-teardown experiment

A failed final write on parent-driven removal now retains the complete job estimate draft in a process-local buffer scoped to its original actor, organization, origin and document. A later editor reopens the in-memory value only after existing access verification, shows a memory-only warning, and prevents submission and disk overwrite. The value is not durable and is lost if the process terminates. Discard is held because clearing the buffer or removing its older persisted version could reveal stale work or delete a concurrent newer version. Safe reconciliation needs shared writer coordination and a trustworthy compare-and-swap; this change does not provide it. Buffer lifetime, logout and privacy behavior, unresolved create/link outcomes, and parent teardown while requests are in flight remain review concerns. This is a held experiment, not release-ready.

The scoped generic buffer and actual store singleton were exercised in lightweight macOS checks (`/tmp/thorbis-estimate-teardown-green.log`, `/tmp/thorbis-teardown-store-green.log`); these used simplified draft types and do not test SwiftUI. The new Swift unit and UI cases are syntax-parsed only. The UI fixtures simulate a parent closing the actual job sheet, both on first write failure and after a successful autosave followed by failure and an attempted discard; no simulator run has yet qualified them.

## Disconnected create-only recovery-copy experiment

A separate held `EstimateRecoveryCopyStore` can write an independently identified, device-protected copy without replacing the canonical draft. A hard-link install is create-only; replay of the same ID succeeds only if the exact encoded scoped record is already present, and a different value with the same ID is refused. Reads reject a different supplied scope and nonregular/symlink files. It is not wired to the buffer, editor, session, logout or discard paths, and caller-supplied scope is not authorization. There is no fsync/power-loss claim, iOS data-protection qualification, sign-out cleanup, record discovery or removal. Noncooperating writers and scope/session authorization remain separate obligations; this is not complete reconciliation.

A macOS exact-source harness passed scoped read/replay/conflicting-content checks (`/tmp/thorbis-recovery-copy-green.log`). A second harness raced two separate processes attempting different values under one ID and observed one winner and one rejection (`/tmp/thorbis-recovery-copy-race-green.log`). Source/harness hashes are `/tmp/thorbis-recovery-copy-hashes.txt`. The initial red is a missing-source compile failure, not behavioral red. The new XCTest was syntax-parsed only; no simulator or device test ran.

A follow-up macOS fault-injection harness observed a retained exact copy after a reported readback failure, then successful read and replay; a synthetic pre-write disk-full error left no installed copy (`/tmp/thorbis-recovery-copy-failures-green.log`). This does not simulate interruption, a real full filesystem, iOS file protection or power failure. The two-process contention harness was rerun against the changed source (`/tmp/thorbis-recovery-copy-race-green.log`).

The earlier `/tmp/thorbis-recovery-copy-hashes.txt` describes the first prototype, not the fault-injection follow-up. On frozen source commit `389fac6`, all three standalone harnesses were rebuilt and rerun: scoped copy/replay (`/tmp/thorbis-recovery-copy-final.log`), competing processes (`/tmp/thorbis-recovery-copy-final-race.log`), and injected read/write errors (`/tmp/thorbis-recovery-copy-final-failures.log`).
