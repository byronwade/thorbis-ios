## Immediate findings

- Opening an estimate currently opens a read-only technician detail. Sent/declined records expose a separate **Revise estimate** sheet. Drafts have no existing editor/update request in native code; approved estimates cannot use native revise. Merely removing the button/sheet would not deliver all-status direct editing.
- The native contract has title, integer quantity, unit price, provenance and complete option packages. It has no document notes, hours/hourly-rate fields or customer visibility settings. There is no persistence path for those controls in these DTOs. The backend agent must distinguish missing native projection from missing canonical contract.
- Long prose currently loses data when typed as a custom estimate line: `String(...prefix(200))` silently truncates. Revised estimate lines reject >200 UTF-16 units, invoice lines >211 Unicode scalars. New-estimate validation inconsistently lacks title/description length checks. Text-field height limits are viewport limits, not character limits, but make paragraphs difficult to work with.
- Existing staff catalogue picker is useful reusable infrastructure. It is not a customer cart/quote/acceptance contract. Do not expose raw catalogue or implement client-derived checkout from it.

## State, copy/save/issue and provenance

`EstimateRevisionEditorState` (`EstimateRevisionEditorState.swift:91`) captures immutable original `estimate`, editable `title`, main `lines`, and `options`. It copies each original line retaining originalLineID and trusted manual/price_book identity (:97–109, :246–275). Unsupported provenance is represented explicitly, blocks save, and is never silently made manual (:115–119, :209, :248–260). Original catalogue wording/price are retained for Edited/Reset.

Current `canRevise` is **sent or declined only** (:111–113). Request construction (:204–243) requires currentRevisionNumber >0, `estimate_option_signing` feature for any options, discount capability for negative lines, valid option identity, and returns `FieldEstimateReviseRequest(expectedRevisionNumber,title,lines,options)`. Main lines and each option have their own 500-line bound; options max eight. Group is explicitly display-only until server stores it (:60); group-only changes are not persisted in request or hasChanges comparison. Do not promise Work/Materials persistence across reopen.

`EstimateRevisionEditorView.swift:30–49` adds current account gates: estimate.create/estimates, estimate_option_signing, estimate.discount, pricebook.view/price_book. `canSave` (:71–75) requires changes and supported provenance. Existing form has title/customer, lines, add/remove complete packages and package title/description. `save` (:348–366) constructs request, POSTs revise, publishes returned record, then dismisses. On 409 retains local edits and offers destructive reload confirmation; `reloadLatest` (:369–381) replaces state only after confirmed fresh GET. No autosave, durable local draft or financial queue exists here.

API boundaries:

- `FieldAPI.swift:1064–1067`: GET estimates/detail, POST `/v1/estimates` using `FieldEstimateCreate` (:812). Create fields: customerId/title/lines/locationId; no options in current native create DTO.
- `FinancialActionAPI.swift:4–23`: revise and option request DTOs. :252 POST `/v1/estimates/{id}/revise` replaces via canonical revision command; no draft update endpoint is wrapped in Swift.
- :225 POST send includes expectedRevisionNumber; :231 approve includes revisionNumber, optional deposit/signature; :246 decline includes revisionNumber.
- :256 invoice lines replacement is POST `/v2/invoices/{id}/lines` with expectedLinesRevision; :260 issue includes expectedLinesRevision. Preserve invoice source links, override reason and separate issue boundary.
- `NewEstimateView.swift:202–235`: create-once `created` record held in memory; if job-link fails retry only links same ID. Discard guards prevent dismissing uncommitted edits. It currently dismisses after successful create/link. Creation has no durable operation receipt across process death.
- `FieldOutbox.swift:7–9, :50–57`: operational progress/note actions, not financial estimate revisions. Do not queue money/signing through it or label unsaved estimate edits queued.

**Required contract resolution before full direct canvas:** canonical draft edit/save semantics; approved/signed-record replacement draft semantics without changing signed revision; revision history/current identity retained; option creation path; missing text/settings projections and write fields. Opening canvas must not create a revision just by viewing. User-visible editing can be direct while canonical revision creation remains the explicit save boundary. Do not widen `canRevise` locally and assume the server accepts draft/approved.

Invoice draft exposes optional unitLabel from provenance, but sends no editable unit label (`InvoiceLineEditorState.swift:33–56, :211–242`).

No native model/persistence for show/hide quantity, rate, hours, description, line price, labor breakdown or document-wide presentation settings was found. Search across Sources for corresponding visibility/hourly/settings fields yielded no such financial setting. `CustomerLinesCard.lineDetails` (:912) always displays description, quantity and each price; technician CommercialLineView always displays quantity×unit price. There is no existing switch to wire up.

Needed canonical decisions: exact supported settings fields/defaults and owner (document/revision/company), projected immutable settings in issued revision/public action/PDF, labor quantity vs hours vs unit semantics, calculation precision/rounding, whether descriptions may be hidden for presentation while remaining signed scope, and validation that all presentations retain exact accepted commercial meaning. Do not invent these in Swift or persist only UserDefaults. Preserve internal costs/margins/provenance privacy.
