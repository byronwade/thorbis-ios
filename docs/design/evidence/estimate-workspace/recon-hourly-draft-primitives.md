## 1. What “hourly” already means

**Trusted catalog facts exist, but structured hourly pricing does not.** Price Book owns immutable revisions containing `description`, `unit`, `sellPrice`, `taxClassification`, `kind`. `kind` is the enum `service | labor | material | assembly`. `unit` is trimmed persistable free text,1–32 Unicode code points, not an enum or duration unit. Price is nonnegative integer USD cents up to100,000,000. There is no hourlyRate, duration, quantity scale, fractional step or rounding-policy field in these owner contracts (`domains/price-book/src/schemas.ts:3–10,52–66,83–92,113–145`). Exact revisions are tenant-bound through `PriceBookRepository.findExactRevision(organizationId,itemId,revision)` / `findSelectableRevisions(organizationId,references)` (`ports.ts:43–73`). A `labor` item may legitimately be priced per job/day/visit; labor alone cannot prove “hours.”

The canonical web picker receives the synced server unit/kind, maps assembly to service for UI grouping, and converts persisted cents to dollars at one seam (`apps/web/src/features/document-builder/price-book.ts:22–40`). Builder addFromPriceBook copies `bookKind`, `unit`, quantity and unitPrice into local lines (`packages/ui/src/patterns/document-builder/lib/store.ts:733–753`). This is useful presentation precedent, not structured hourly authority.

The separate web Price Book management page has a `flat | hour` selector and `/hr` rendering, but source explicitly says this authoring surface remains **on this device** because server canonical fields do not match its extra code/name/category/image model (BYR-327). `useState<'flat'|'hour'>`, parseFloat→Math.round cents and `addPriceItem` are local authoring (`apps/web/src/features/price-book.tsx:40–50,73–90,215–219,263,315`). Do not treat this local enum as a server-owned unit taxonomy or migrate it implicitly.

**Estimate provenance currently loses the catalog unit/kind.** Estimates’ `PriceBookRevisionSnapshot` port carries only `{description:string,unitPrice:Money}` (`domains/estimates/src/ports.ts:124–151`); estimate source stores original description/price, not unit/kind (prior recon schema anchors). Its commercial paper emits `unit:''`. Direct invoice Price Book sources do have retained originalUnit/originalItemKind for newer contracts; those facts are provenance, not an enum defining hours (`domains/invoicing/src/direct-price-book-line-authority.ts:30–34,165–177,219–230`). Historical sources may lack them. Do not look up the current mutable catalog to infer the unit of old signed paper.

**Existing display choices are broader than native-only toggles.** Web `PdfDisplay` includes title/description/quantity/unit/rate/lineAmount, recipient/contact/date/job reference/notes/signature/photos and more; flat hides quantity/unit/rate, T&M shows them, full adds markup (`packages/ui/src/patterns/invoice/pdf-display.ts:1–93`). Reuse product vocabulary where appropriate, but do not expose internal markup/cost by copying the local full-breakdown preset into a customer contract. Shared hashed `CommercialDocumentContent.visibility` is the canonical renderer reuse point established in the earlier report.

**Minimal truthful extension:** freeze canonical line unit/kind facts through Estimates, revision/acceptance, quotes and invoice copy. Use a versioned structured measure/billing basis distinguishing hours from generic quantity; derive `/hour` only from that trusted basis. Preserve legacy free-text unit display without guessing semantic aliases. The editor may display/hide known hours independently from generic quantities, but toggling visibility cannot alter price or quantity. If fractional hours are required, choose explicit server-owned scaled quantity or rational duration, input precision/step and a versioned minor-unit rounding rule before implementation; apply the same rule in TS, SQL, quote/acceptance and billing. No existing owner type audited here supplies this missing policy. Whole-hour-only support would be an explicit product constraint, not full fractional hourly support.

## 2. Durable draft save: reuse platform receipts, add owner semantics

**Existing durable operation receipt store:** `platform.processed_commands`, tenant-scoped/RLS, primary identity `(organization_id,command_id)`, fields actor/device/command/result/optional domain intentFingerprint/clientCreatedAt/processedAt (`packages/database/src/index.ts:115–150`). Do not add a second draft receipt table or store replay solely in process memory.

Actual reusable persistence signatures (`packages/database/src/platform.ts:201–212,282–293`):

```ts
findOrLockProcessedCommand(tx, organizationId, commandId)
  -> Promise<{command, actorUserId, result, intentFingerprint?} | undefined>
recordProcessedCommand(tx, {
  commandId, organizationId, deviceId, actorUserId, command,
  result, intentFingerprint?, clientCreatedAt
}) -> Promise<void>
```

`findOrLockProcessedCommand` takes tenant+command transaction advisory lock **before** SELECT, then performs an exact tenant+UUID lookup; a hash collision only serializes unrelated work (`platform.ts:214–246`). `recordProcessedCommand` writes in the same transaction as the mutation; PK remains final invariant (`274–316`). Invoice create/update use the ordinary fingerprint column, not the legacy Jobs-specific JSON wrapper. Reuse through `DomainDeps.commandLedger` / existing dispatcher adapter, not direct new SQL from a domain (`services/api/src/app.ts:1699–1700`; `commands.ts:131–159`).

`applyCommand(deps:CommandDispatchDeps,envelope:CommandEnvelope):Promise<CommandOutcome>` runs authenticated transaction, validates envelope/catalog/policy, binds `ctx.command={id:commandId,clientCreatedAt}`, then ledger arbitration before domain execution (`services/api/src/commands.ts:223–273`). Envelope has commandId/deviceId/actorId/organizationId/policyVersion/command/clientCreatedAt/payload (`packages/sync/src/envelope.ts:33–63`); uploaded tenant/actor are validated against authenticated context, not trusted authority. Same ID for another command/actor conflicts. Same actor may retry from another currently authorized device; device is provenance (`commands.ts:275–296`). Source-aware `beforeApply` runs after receipt lookup for first application only (`515–540`). Domain mutation and ledger record are atomic.

**Invoices own semantic fingerprint/replay checks.** `parseUpdateInvoiceLinesIntent(rawInput) -> Promise<{input,fingerprint}>` parses the owner schema then hashes canonical intent. Canonicalization sorts object keys, lowercases ID values, sorts only set-like overriddenFields; ordered lines are preserved. Fingerprint is `v1:sha256:<hex>` (`domains/invoicing/src/schemas.ts:660–692,728–735`). This function is invoice-owned/private policy, not a global generic hash contract to import blindly into Estimates.

Dispatcher computes and compares the digest before replay target loading; malformed or changed reuse conflicts, missing legacy invoice fingerprint refuses; accepted exact replay calls owner verifier (`services/api/src/commands.ts:330–362,449–494`). `replayUpdatedInvoiceLines(ctx,deps,rawInput,rawAcceptedResult) -> Promise<{result:Invoice,intentFingerprint:string}>` validates receipt shape/tenant/invoice binding, reads current invoice, reauthorizes invoice.edit and accepted source concession, and returns **current invoice** with the digest, not blindly the historical JSON (`invoicing/commands.ts:1330–1361`). A draft update must make its replay response semantics explicit; do not assert every existing replay returns original immutable result.

**HTTP caveat:** direct `POST /v2/invoices/:id/lines` calls `runPrepared -> updateInvoiceLines`; `runPrepared` establishes authenticated/gated transaction then executes work and has no command-ledger arbitration (`services/api/src/app.ts:1422–1488,5193–5217`). v1 is mounted as migration-required refusal (`5175–5191`). Therefore “follow invoice updateLines” gives version safety but does not automatically give durable same-operation response-loss recovery to a new direct HTTP route. Plan either routes save through the established registered command envelope/dispatcher or deliberately adapts the same platform ledger semantics for direct HTTP. Do not describe an arbitrary operationId body/header as an existing implemented API.

### Version and lock primitives suitable for updateEstimateDraft

- Existing `EstimateRepository.findByIdForUpdate(organizationId,id):Promise<Estimate|undefined>` is mandatory for mutating read/decide/write; SQL uses tenant-filtered `SELECT ... FOR UPDATE` (`domains/estimates/src/ports.ts:91–102`; persistence/repository.ts:363–372). Reuse it under the transaction after command arbitration.
- Existing estimate `currentRevisionNumber` is the last **issued** paper pointer, not a draft edit counter. Existing `offerWriteEpoch` is explicitly repository-owned writer-awareness fence and absent from DTO/replica; it is not a public concurrency version (`estimates/persistence/schema.ts:52–66`). updatedAt is not a monotonic draft compare-and-swap token.
- Invoice `linesRevision` is a real precedent: bounded integer1…Number.MAX_SAFE_INTEGER, incremented by every line-changing operation including discount so stale replacement cannot erase it (`invoicing/schemas.ts:390–400`). Owner command authorizes before stale/version conflict details, locks and refuses non-draft/ledger-bound edits (earlier recon).
- Invoice repository calls `billing.update_invoice_lines_v1(p_id,p_organization_id,p_expected_lines_revision,p_lines,p_actor_id)` then reloads persisted row (`invoicing/persistence/repository.ts:300–324`). SQL authoritatively enforces the write via dedicated invoice-writer authority; do not reuse this invoice-specific definer/role for Estimates (`migrations/0088_direct_price_book_invoice_sources.sql:523–589`). Reuse the pattern of independent SQL protection and authoritative returned state.

**Concrete proposed interface boundary, still new work:** Estimates owns new draft revision/counter + canonical draft-update input covering title/lines/options/offers/long text/display/measure fields, expected draft revision and expected issued lineage as needed. New `parseUpdateEstimateDraftIntent` and read-only `replayUpdatedEstimateDraft` should follow the actual invoice signatures and reauthorize current estimate.create/resource/credits, with explicit canonicalization and durable replay response. Register the command/catalog/schemas/queue/projectors/feature gates and use the existing platform ledger. Every commercial draft mutation must advance the edit revision, and send must compare the exact edited draft version in addition to issued lineage so a late autosave cannot issue different content. Preserve C1 aware-offer fences and refuse unaware versions. First-draft update and replacement-draft update share the authority; approved/signed state still routes to C2 change order, never this mutator.

Exact replay after another save or send must not reapply, decrement versions, resnapshot new Price Book prices, overwrite newer lines or append duplicate audit/outbox. A changed payload with the same command ID must conflict even when its expected revision is now stale. These requirements can use existing receipt infrastructure; the new draft version and owner fingerprint/replay semantics are the genuine missing pieces.
