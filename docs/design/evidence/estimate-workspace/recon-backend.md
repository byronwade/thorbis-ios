## Findings that change the design

1. C1 at this pin publishes/freeze-renders optional bundles, but intentionally refuses their approval. Customer selection, quote, signature/acceptance and source-aware held admission remain Task3/4. A customer-facing cart cannot safely be enabled by Swift alone.
2. The technician can open an editor directly as a UX choice, but the existing estimate API cannot persist ongoing edits to an existing draft. `reviseEstimate` creates a replacement draft and only accepts an identical replay once that draft exists. A canonical versioned draft update is a real backend dependency.
3. Paragraph support needs contract work. Estimate descriptions are 200 UTF-16 units, option/offer descriptions 500; invoice lines are 211 Unicode code points. Estimates and invoices do not currently have editable document-wide notes/body fields. Job notes already allow 10,000 units.
4. There is a reusable hashed visibility mechanism in shared Documents, but no persisted customer display profile in the audited Estimate/Invoice write/revision DTOs. Both owning projections currently emit `visibility: []`. Reuse this mechanism; do not create native-only visibility booleans.
5. Commercial lines contain description, integer quantity and price, not separate labor hours/rate semantics. Hiding quantity/unitPrice is supported by generic snapshot rendering; independently configurable hours requires canonical semantics rather than guessing that all quantities are hours.

## Technician draft/revision and invoice boundaries

Sources: `domains/estimates/src/schemas.ts:305–377,385–476`; `commands.ts:304–378,680–845`; `services/api/src/app.ts:3343–3385`; `services/api/src/routes/manifest.ts:3585`.

Existing commands are create, send, approve, decline, requestChanges, revise; there is no estimate update/save-draft command in audited owner/API contracts. `POST /v1/estimates/:id/revise` accepts full title/lines/options/offers and expected issued revision number (minimum1). It locks/authorizes, validates exact predecessor, then creates replacement draft from issued paper. If already draft, an identical payload returns it; a different payload conflicts (`commands.ts:778–796`). This also means first draft, with no issued revision number, cannot use revise as an update API.

RequestChanges returns a sent aggregate to draft while retaining prior paper, without rewriting historical revision. Send compares expectedRevisionNumber (zero for never-issued), inserts the next immutable revision, freezes recipient and commercial terms, supersedes predecessor atomically (`commands.ts:319–378`). Revision GET and revision-document endpoints already exist. Revision is therefore the default persistence behavior of editing issued unapproved paper, but need not be an extra user-visible action/button. Opening the canvas itself should remain a read/local edit action; saving performs the required canonical transition, issuing is a deliberate separate boundary.

Approved estimate revise conflicts: “an approved estimate requires a change order; it cannot be revised in place” (`commands.ts:784–786`). Preserve approved/signed scope and show the same editor surface backed by a new change-order/addition authority, not mutation of the approved document. This rule is commercial approval-based, not contingent on whether an invoice has already been created.

Invoices already have a canonical draft-update pattern: `updateInvoiceLines` takes expectedLinesRevision, authorizes before exposing conflict details, locks and rejects non-draft or ledger-bound updates (`domains/invoicing/src/commands.ts:1192–1230`; `schemas.ts:712–741`). Issue requires that exact line revision and writes immutable issued snapshot/recipient with lifecycle atomically (`commands.ts:1364–1409`; `schemas.ts:537–555`). Reuse this concurrency approach for estimates. Issued invoices cannot be edited through updateLines; preserve discount/credit and provenance authorities. A pending draft with ledger binding can also refuse edits.

Completion billing uses the shared job lock with schedules; a schedule owns billing even if closed/descoped, so completion returns that authority rather than creating a second invoice (`invoicing/commands.ts:1028–1048`). Original sourceEstimateId/revision is copied into completion invoice birth (`commands.ts:1084–1085`). C2 must extend source admission rather than erase this binding.

Long prose cannot be solved by a multiline Swift TextField. Minimal extension: keep short title/source label identity; add optional versioned canonical long plain-text body/details fields at document and line level, with explicit paragraph/newline semantics, public vs internal note distinction, safe bounded text and aggregate byte limits. Use one owning schema per field across input/persistence/revision/acceptance/API/PDF/invoice-copy; avoid forcing Price Book source originalDescription to become a paragraph just to carry editable sales details. The exact field names/bounds require design decisions and are recommendations here, not existing APIs. If adding long details alongside description, selected scope hashing and invoice provenance need to copy/check them, not drop them.

Rendering limits currently remain real: Forme title240, body4000, cell1000, rows500, sections512 (`packages/documents/src/forme.ts:17–23`); appendix body4000, table500, aggregate4500 (`appendices.ts:3–30`). Legacy no-appendix fallback deliberately truncates >58 descriptions (`documents/src/index.ts:329–333`), while new appendix mode wraps using physical metrics. Do not infer universal full-text fidelity from the C1 appendix repairs. ## Customer display settings: reuse and missing owner contract

Reusable truth: `CommercialDocumentContent.visibility` is domain-resolved `{field,visible}[]`, with immutable template/renderer references (`packages/documents/src/snapshot.ts:108–113`). Snapshot contentHash hashes canonical UTF-8 content including visibility, preserving exact strings (`snapshot.ts:124–136`). Snapshot renderer respects hierarchical visibility and always suppresses internal fields (`snapshot-render.ts:134–144`). Line fields use `lines.description`, `lines.quantity`, `lines.unit`, `lines.unitPrice`, `lines.total`; option/offer prefixes also defer to shared lines fields (`snapshot-render.ts:197–225`). Presentation supports column choice and cannot force hidden snapshot fields visible (`presentation.ts:21–31,154`). This is the existing reuse point.

Missing owner wiring: estimate and invoice commercial projections hardcode visibility:[]; estimate scope/exclusions/warranty/terms also empty (`estimates/documents.ts:284–289`; `invoicing/documents.ts:178–183`). Estimate/Invoice persisted schemas and issue snapshots contain no display profile. Direct estimate DocumentModel always emits quantity/unitPrice and needs parity (`estimates/documents.ts:112–118`). Public action DTO always includes base quantity/unitPrice, with no profile; native/web review cannot derive approved settings today (`document-actions.ts:104–179`). A renderer hiding a value is not itself a guarantee the public JSON omits it.

Recommended minimal canonical extension: an Estimates/Invoicing-owned versioned display profile (document-level defaults plus bounded per-line overrides only where needed), frozen into issued revision/snapshot; resolve it to existing shared visibility/presentation. Public safe projections and native DTOs must receive the canonical resolved display contract, and exposure tests must verify hidden internal details are absent where required. Keep total/consent/selected scope intelligible and exact. Retain full internal pricing/provenance even when visual rates/quantities are hidden. Profile changes on issued unapproved paper require replacement issue/new hash; approved paper remains historical. Missing legacy profile must preserve prior bytes/hash and default behavior, not retroactively insert defaults into old snapshots. Company preference changes affect new drafts only.

Hours/rates: current estimate lines have only description/quantity/unitPrice/source, and commercial `unit` is emitted empty (`estimates/documents.ts:180–198`). A profile can govern existing quantity/price columns; distinct labor hours/rate visibility needs source-backed line/unit/kind semantics if not supplied elsewhere. Do not relabel every quantity as hours or use hidden hours to change money. Keep discount/credit visibility and totals consistent; do not drop negative lines or authorization because a customer-facing field is hidden.

## Recommended phased implementation dependencies

1. **Canonical editable drafts and text/display schema.** Define owner fields, legacy-preserving defaults, explicit text units/limits, versioned draft concurrency and source-preserving updates. New draft-save command must support initial and replacement drafts; `revise` transition remains under the editor. Add successor migrations/independent SQL guards and writer compatibility. Invoice update remains draft-only; append-only job notes remain corrections-by-new-note.
2. **Shared paper parity.** Freeze new text/profile in estimate revision/invoice issued snapshots; extend exact content/hash and accepted/invoice-source copy checks; wire public safe DTOs, shared web render, direct/snapshot PDFs and future native. Verify full paragraph retention, newlines/Unicode, column hiding, historical no-field hash preservation, overflow/413 and page/resource bounds.
3. **Complete C1 Task3/4.** Apply existing planned exact quote/acceptance and API/held admission with expanded frozen contract. Do not implement UI money recalculation as authority. Require PostgreSQL concurrency/raw SQL/RLS/upgrade, missing evidence fail-closed, legacy writer and rehold qualification; existing signed paths remain.
4. **C2 additions/bill-once.** New approved additions retain original job estimate/revision, derive canonical admission under shared job lock and coexist with schedules/deposits/credits. Review estimate lifecycle, billing source uniqueness and retries together.
5. **C3 editor/storefront.** Technician opens editing canvas immediately; server handles draft save/revision/change-order transitions. Customer browses published extras, opens full details, chooses eligible quantities, adds/removes cart entries, re-quotes on change, reviews exact work/total, signs once, receives accepted-scope confirmation. Preserve all existing estimates/invoices/job notes; no optional defaults; no hidden feature loss. Payment checkout consumes approved invoice/payment authority only when available.

These phases may be split into smaller implementation plans by owner, but contract interfaces must be fixed before independent UI execution.
