# Proposed invoice denial coordination

Status: held design; no app behavior changed. 2026-11-04.

## Problem and current boundaries

A resource denial has to retire both the invoice and its payment history across mounted views, prevent old cache writes or a relaunch from reintroducing them, and avoid losing queued or already-recorded money. A no-signal read with no observed denial must continue to use a properly scoped saved copy. An offline device cannot learn about a remote revocation it has not observed.

The current in-process WIP (`/private/tmp/thorbis-customer-invoice-denial-1104`) has `InvoiceResourceDenials` in `InvoicePaymentCollection.swift`: a main-actor registry and subscribers for invoice and history denials. It does not survive process death, and `InvoicePaymentCollectionModel` also reads/writes `JobDetailCache` (`OfflineSupport.swift`), which is keyed only by ID. `APIClient.sendData` in `API.swift` serves and asynchronously schedules `SavedCopyStore` writes; `SavedCopies.swift` scopes those by a sanitized actor/workspace string, while origin is in the path key. A cancelled task checks cancellation before inspecting HTTP status. `fieldInvoices`, `fieldJobInvoices` and `fieldPayments` page separately; a collection can hold the same invoice as a detail. Other visible consumers include `JobCommercialDocuments`, `CustomerJobCompilation`, `FinancialViews`, `OwnerHome`, `SearchViews`, and job closeout in `JobOperationsViews`. `FieldOutbox` and `InvoicePaymentIntentStore` own payment intent, separately from these caches.

The app entitlement includes an app group and a widget target exists. The reviewed cache paths use application-support directories and the widget target does not compile `API.swift`, `SavedCopies.swift`, `OfflineSupport.swift`, or `InvoicePaymentCollection.swift`; this source inspection does not prove every possible extension, shared-container reader or future target is excluded. Before relying on single-process ownership, audit the built targets and enforce the boundary.

## Proposed coherent boundary

1. Put every invoice and history response, including list pages and fallback paths, through one main-actor resource owner. Scope by independently validated actor, organization, canonical origin and invoice ID; record history separately and bind it to its invoice version. Capture current session, authority and API generations at request start and check again before every publish. Do not rely on the currently sanitized concatenated saved-copy scope as proof of collision-free identity, or assume actor IDs are UUIDs without verifying the actual session contract.
2. Before any potentially authoritative live request for a known resource, durably install its pending/held state. If this cannot be persisted, do not issue that mediated request. Classify the actual response status before cancellation discards it, and preserve denial observation through terminal callbacks; serialize or coalesce overlapping requests without dropping a newer or older denial. A crash while pending leaves a hold. A fresh verified network response can recover only its own resource; a history recovery also requires the current invoice relation. A known-offline operation with no new request should not first create a pending hold.
3. The transport supplies explicit per-response origin and complete-page provenance rather than `savedCopyDate(path)`, which is mutable path-level state. A cache grant names a digest/version of actual stored bytes. A write for an old response cannot install or mark new bytes authorized after denial or a newer epoch. The existing asynchronous `SavedCopyStore` write queue must be mediated at execution time, not merely checked before enqueue. A replacement and marker protocol must address partial writes, rename and directory-sync failures; the held fence's final-sync ambiguity is not a finished design.
4. A denial transition is delivered synchronously on the main actor to all registered in-process owners before any further model publication: clear matching invoice, history and actionable/sign/payment state, dismiss readers, advance epochs and render a truthful unavailable state. A matching list removes/marks that item unavailable and remains explicitly partial; closeout must never infer a zero balance or completed requirement from the omission. History-only denial clears history and disables operations requiring complete history without falsely denying the invoice itself. Do not delete or alter payment intents, pending outbox commands, idempotency keys or recorded-payment reconciliation when retiring reads.
5. For a cold launch, read only a verified, digest-matching snapshot under a stable actor/workspace/origin/resource authority record with a bounded expiry. A denial or incomplete live attempt survives restart. The authoritative stable identity, expiry and job/customer relationship proof are not yet established; legacy `JobDetailCache` and list caches cannot be blessed by merely wrapping their bytes. Until a safe migration is proven, hold integration rather than silently claiming scoped offline access or globally suppressing unrelated offline workflows.
6. Keep a single observable owner shared by every mounted scene in the app process, including detail, document drawer, finance list and closeout. Do not use the held presentation lease as the product: it prevents normal refresh while displayed. If another process can actually access these records, in-process notifications are insufficient. Require a proven cross-process invalidation/acknowledgement protocol and mediated cache, or keep that target out of the data boundary. A model update schedules SwiftUI rendering; tests must separately establish sheet and action retirement and cannot prove instantaneous physical pixel removal.

## Verification before exposure

- Real transport: 200 A → 403/404, two mounted views and an open drawer; old responses and child-page late denial; cancellation immediately after response; history-only denial; actor/workspace/origin/session change; successful recovery requires matching fresh response and current scope.
- Cache: queued A write delayed across denial and live B; list page containing denied invoice; replacement before/after ledger transition; injected failures before write, after rename and at directory sync; process death at every transition; relaunch offline after denial and ordinary offline after an undenied verified snapshot. Verify no cross-scope data and explicit legacy behavior.
- Financial: queued and recorded cash/check preserve exact idempotency keys across denial/relaunch; unknown history cannot double-count or mark closeout paid; unrelated invoices remain usable; restore access and reconcile once verified.
- Lifecycle: sign-out and workspace switch during reads/writes, protection/lock behavior on actual signed iOS device and extension membership, plus no loss of currently authorized offline work. Never use production credentials or shared user data in fixtures.

The held `/private/tmp/thorbis-invoice-denial-store-1104` fence and `/private/tmp/thorbis-customer-invoice-denial-1104` UI candidate are experiments only. Neither is a complete implementation or approved for release. The presentation-lock prototype is intentionally excluded from the proposed product path.
